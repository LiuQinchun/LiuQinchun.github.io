1.2 TCP连接全流程

1.2.1 TCP三次握手



由1.2中的图可知

  1. No.3 报文段中，客户端向服务器的 8081 端口发送 TCP SYN 报文段，请求建立 TCP 连接。由于 Wireshark 启用了相对序列号显示，此时 Seq=0。TCP Window接收窗口为 64240 字节，MSS 最大报文段为 1460 字节。

  2. 随后No.4报文段中服务端8081端口向客户端60798临时端口返回了SYN和ACK的Flags，Seq序列号为0，ACK确认号为No.3报文段中Seq值+1。表示我已收到客户端的同步请求，并且我同意你的连接。服务器通过 Ack=1 表示：客户端发送的 SYN（Seq=0）已经收到，我期望从客户端的 Seq=1 开始接收后续数据。

  3. 最终No.5报文段中，客户端向服务器8081端口发送ACK的Flags，Seq=1，Ack=1。客户端已经收到服务器的 SYN（服务器 Seq=0），因此期望服务器下一次发送的数据序列号为 1。Ack=1表示确认号值在No.4报文段中Seq=0+1得到。

就此TCP三次握手成功建立，可以开始传输数据。

TCB 传输控制块，打开后服务器/客户端进入监听（LISTEN）状态

SYN TCP报文标志位，该位为1时表示发起一个新连接ACK TCP报文标志位，该位为1时，确认序号有效,确认接收到消息。TCP规定，在连接建立后所有报文的传输都必须把ACK置1seq sequence number，报文初始序列号，代表发送的第一个字节的序号ack acknowledgement number，报文确认序号，代表希望收到的下一个数据的第一个字节的序号

由1.2中的图可知：

No.10 报文段中，客户端向服务器发送 FIN+ACK 报文段，Seq=407，Ack=1051，表示客户端已经没有更多数据需要发送，并请求关闭客户端到服务器方向的 TCP 数据流。

HTTP实验报告

实验时间： 2026年9月28日客户端： 192.168.9.209服务器： 192.168.9.76服务器端口： 8081

正常登录：

  • 请求方法和路径： POST方法，对8081\login.php请求登录
  • 是否出现用户名和密码： 由于网站是HTTP协议，所以明文暴露用户名和密码
  • 是否携带 Cookie： 每次客户机向服务发送请求都会携带Cookie，并且Cookie值始终相同。
  • 服务器返回的关键内容： POST登录身份认证通过后，服务端返回302临时重定向，随后客户端下次向index页面发送了GET请求报文
  • 登录成功的证据： 客户端向index.php页面发送GET请求后，服务端返回的响应报文状态码200，页面成功加载

错误登录：

  • 请求和正常登录相比改变了什么： 302临时重定向指向login.php页面，准备重新登录

  • 是否使用了相同 Cookie： Cookie值始终相同

    “Cookie 值始终相同”不等于“Cookie 就是登录状态”。它可能只是 PHP 的会话标识。你还需要做三次对比：

    1. 登录前访问页面
    2. 登录成功后访问受保护页面
    3. 删除 Cookie 后再次访问受保护页面

    只有这样才能确认该 Cookie 是否真正决定登录状态。

  • 服务器返回的关键内容： 返回302临时重定向

  • 能否从抓包判断登录失败： 可以，抓包后观察是否有服务端的响应报文，状态码是否是HTTP 200 OK。或者观察302临时重定向指向哪里。

登录后访问：

  • 请求是否携带登录状态： 是，携带

  • 登录状态具体保存在哪里： 保存在Cookie

  • 不带该状态时会发生什么： 返回401未授权，302临时重定向指向login.php（根据理论，我猜的）

    错误登录不能只靠 302 判断。302 只是重定向，具体是成功还是失败，要看：

    • Location 指向 index.php 还是 login.php
    • 后续客户端请求了哪个页面
    • 后续请求是否成功访问受保护资源
    • 响应内容是否包含登录成功或失败信息

    失败登录后登录页也可能返回 200，所以“是否 200”不能单独作为登录成功标准。

安全结论：

  • HTTP 明文暴露了什么： 暴露了整个请求体和响应体，以及Cookie值，相当于裸奔。
  • 如果攻击者只能监听流量，能否复用登录状态： 直接套用Cookie，冒用身份，甚至还可以数据重发
  • 服务器应该如何降低风险： HTTPS 可以保护客户端到服务器之间的传输内容，降低网络监听导致的账号和 Cookie 泄露风险，但不能单独解决身份认证、权限控制和终端被入侵等问题。

2 Pikachu越权实验报告

实验环境：

  • 攻击机：Kali Linux，IP：192.168.240.209/24

  • 靶场服务器：Arch，IP：192.168.240.76/24

  • 靶场：Pikachu

    2、登录成功后即可查询本用户的信息，这里通过burpsuite抓包拦截分析查询后的响应包

    3、这里可以看到抓包结果，随后将抓包结果转发给Repeter重发器

    这里抓到包了我们可以仔细分析一波，当前客户端向服务器(192.168.140.76:8081)的 /vul/overpermission/op1/op1_mem.php 路径发送GET请求，携带参数是username（用户名） 和 submit（查询按钮值），携带了SessionID38d4cadbe84e5c1f1cd0625e79dd7f3a 。

    4、在Repeter重发器中我们能看到查询结果的方式是通过GET方法对opl_mem.php文件提交username=lucy的查询参数，这里可以尝试以下修改参数进行水平越权试探。

5、这里通过修改这个参数可以直接访问到其他的用户，说明系统没有校验 ‘’当前登录用户是否有权访问该数据‘’ 。

    当前登录用户为 lucy，在保持会话 Cookie 不变的情况下，将 username 参数修改为其他用户后，服务器仍然返回了目标用户的信息。说明服务端未对当前登录用户与查询目标用户进行权限校验，存在水平越权漏洞。
如果删除 Cookie 后仍可访问，则同时还存在未授权访问问题；如果删除 Cookie 后跳转到登录页，则说明登录校验存在，但水平权限校验缺失。

6、这里在删除Cookie的情况下修改username参数仍然可以访问到其他用户的信息，说明服务器没有身份验证也没有权限验证。

实验总结： 本次实验通过 Burp Suite 抓包和 Repeater 重放，验证了 Pikachu 水平越权模块存在水平越权漏洞。保持 lucy 的会话 Cookie 不变，将 username 参数修改为其他用户后，服务器返回了目标用户信息。进一步删除 Cookie 后仍可访问，说明该接口同时存在未授权访问问题。漏洞成因是服务端未校验登录状态，也未校验当前用户与目标用户的权限关系。修复时应增加登录校验，并从 Session 中获取当前用户，同时增加水平权限校验。

2.2 VPE （Vertical Privilege Escalation）垂直越权

Pikachu垂直越权实验报告

一、实验目的

理解垂直越权漏洞的成因，掌握通过普通用户会话测试管理员专属功能的方法。

二、实验环境

  • 靶场：Pikachu（192.168.240.76:8081）

  • 测试工具：Burp Suite（192.168.240.209）

  • 测试身份：普通用户 user

三、实验过程

  1. 先登录管理员身份，测试服务器为管理员开放了哪些服务。


  2. 登录普通用户账号，保留Cookie以测试是否具备VPE漏洞。

  3. 访问 op2_admin.php 具备身份验证，无法使用普通账号的Cookie访问。

  4. 访问 op2_admin_edit.php，发现添加用户表单可以正常打开。

  5. 使用普通用户提交添加用户请求。

  6. 验证新用户确实创建成功。

四、实验结果

    经实验表明，攻击机（192.168.240.209）访问服务器（192.168.240.76:8081）pikachu的 /vul/overpermission/op2 这个路径检测是否具备垂直越权漏洞。

    1、使用普通用户的SessionID访问op2_admin.php页面（后台管理员控制台）时，服务端存在身份验证，校验SessionID后匹配失败，不准许放行，随后302重定向至/login.php的登录页面进行重新登录。

    2、使用普通用户的SessionID访问op2_admin_edit.php页面时，服务端直接响应HTTP 200/OK 正常响应了 “后台用户添加页面表单” 页面，证明服务端并没有校验用户SessionID是否具备访问上级文件的相应权限，属于垂直越权访问。随后用Burpsuite抓包Repeter重放后直接成功创建了一个用户，恰实证明VPE漏洞存在。

五、漏洞原理

    服务端只检查用户是否登录（即身份验证），却没有检查当前用户是否拥有添加用户的权限（即权限验证），那么低权限用户就可能执行高权限操作，从而导致垂直漏洞的产生。

六、修复思路

  • 在服务端对每个敏感操作实施权限校验。

  • 默认拒绝未经授权的请求。

  • 不要仅依赖前端隐藏按钮或限制页面入口。

  • 对添加用户、修改权限、删除用户等操作分别验证权限。
