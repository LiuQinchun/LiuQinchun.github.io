网络渗透技术

2026-09-13 · 1.2 万字 ·更新 2026-09-24 网络渗透 实践

无线WIFI渗透以及蓝牙渗透

    Wi-Fi 网络 我们先从 Wi-Fi 开始。在本节中，我会向你展示如何查找、检查以及连接到 Wi-Fi 接入点。在此之前，让我们花点时间了解一些基本的 Wi-Fi 术语和技术，这有助于你更好地理解我们在本章中进行的许多查询输出内容：

  • AP（接入点）这是无线用户连接以获取互联网的设备。

  • ESSID（扩展服务集标识符）这和我们在第3章讨论过的SSID一样，但它可以用于无线局域网中的多个接入点（AP）。

  • BSSID（基本服务集标识符）这是每个接入点的唯一标识，它和设备的MAC地址一样。

  • SSID（服务集标识符）这是网络的名字。

  • Channels（频道）Wi-Fi 可以在 14 个频道（1–14）中的任何一个上运行。在美国，Wi-Fi 限制在 1–11 频道。

  • Power（信号强度）你离 Wi-Fi AP 越近，信号越强，连接也越容易被破解。

  • Security（安全性） 这是正在读取的 Wi-Fi 接入点所使用的安全协议。Wi-Fi 主要有三种安全协议。最早的有线等效保密（WEP）非常容易被破解，缺陷很多。它的替代方案是 Wi-Fi 保护接入（WPA），安全性稍微高一些。最后是 WPA2-PSK，它更加安全，使用所有用户共享的预共享密钥（PSK），现在几乎所有的 Wi-Fi 接入点都在使用它（企业 Wi-Fi 除外）。

  • Model（模式）Wi-Fi 可以以三种模式之一运行：托管模式、主模式或监控模式。你将在接下来的部分了解这些模式的含义。

  • Wireless range（无线范围） 在美国，Wi-Fi 接入点在法律上必须将其信号广播的功率上限设为 0.5 瓦。在这种功率下，它的正常覆盖范围约为 300 英尺（100 米）。高增益天线可以将这个范围延长到最多 20 英里。

  • Frequency（频率） Wi-Fi 设计用于 2.4GHz 和 5GHz。现代的 Wi-Fi 接入点和无线网卡通常两者都使用。

    在这里，我们只看到无线接口，也就是网卡，以及关于它们的关键信息，包括使用的无线标准、ESSID是否关闭，以及模式。模式有三种设置：managed，表示它准备加入或已经加入一个AP；master，表示它准备充当或已经是一个AP；monitor，我们将在本章稍后讨论。我们还可以看到是否有客户端已与其关联，以及它的发射功率等信息。从这个例子可以看出，wlan0处于连接Wi-Fi网络所需的模式，但尚未连接任何网络。一旦无线接口连接到Wi-Fi网络，我们会再次讨论这个命令。如果你不确定想要连接哪个Wi-Fi AP，可以使用iwlist命令查看网卡能探测到的所有无线接入点。iwlist的语法如下：

$$
iwlist\ \ interface\ \ action
$$

    你可以使用 iwlist 执行多种操作。就我们而言，我们将使用 scan 操作来查看你所在区域的所有 Wi-Fi 接入点。（请注意，使用标准天线时，你的覆盖范围为 300–500 英尺，但可以通过一个便宜的高增益天线来扩展。）

1 Linux网络命令

1.1 IP 命令

ip 是 Linux iproute2 工具集中的核心网络管理命令。在 Kali Linux 中，它主要用于查看和修改 Linux 内核维护的网络状态。其功能涵盖网络接口、IP 地址、路由、ARP/邻居表、策略路由以及网络命名空间等。

从使用方式来看，ip 可以理解为：

ip [选项] 对象 操作

例如，ip addr 中的 addr 表示“IP 地址”，ip route 中的 route 表示“路由”。因此，学习 ip 的关键不是死记参数，而是理解不同对象对应 Linux 网络中的什么概念。
主要参数与使用示例

1.1.1 ip link（网络接口）

link 操作的是 Linux 的网络接口，也就是系统所认识的网卡和虚拟网卡。

    直接执行 ip link，可以查看当前系统有哪些接口。例如 Kali 中可能出现 lo、eth0、wlan0、tun0 等。

如果看到类似：2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP>

其中 eth0 是接口名称，UP 表示接口已经启用，LOWER_UP 则说明底层链路处于工作状态。

如果希望启用接口，可以使用：sudo ip link set eth0 up

关闭接口则使用：sudo ip link set eth0 down

例如你在 Kali 实验中暂时关闭有线网卡，可以执行 sudo ip link set eth0 down；之后重新启用即可。

因此，遇到“网卡到底有没有启用”的问题，首先应该想到 ip link。

1.1.2 ip addr（IP 地址）

addr 用于查看和配置网络接口上的 IP 地址。

最常用的是：ip addr ; 它也可以简写为：ip a

例如输出中可能出现：inet 192.168.1.20/24

这里的 192.168.1.20 是 IPv4 地址，而 /24 表示网络前缀长度。

如果只想查看 eth0：ip addr show eth0

如果只查看 IPv4：ip -4 addr

如果只查看 IPv6：ip -6 addr

ip a 在日常 Linux 网络排查中非常常用。例如你的 Kali 突然无法访问 Ubuntu 靶机，第一步就可以执行 ip a，确认 Kali 是否仍然具有正确的 IP 地址。

如果发现原本应该是 192.168.1.20/24，现在却没有 IPv4 地址，那么问题就已经缩小到 DHCP、网络配置或接口状态等范围。

ip addr 也能够修改地址。例如：

sudo ip addr add 192.168.1.50/24 dev eth0

表示给 eth0 添加 192.168.1.50/24。

删除则可以使用：

sudo ip addr del 192.168.1.50/24 dev eth0

这里需要注意，ip addr 的修改通常直接作用于当前运行中的网络状态，并不一定意味着系统重启后仍然保留。因此，它和 /etc/network/interfaces、NetworkManager 等持久化网络配置并不是同一个层次。

1.1.3 ip route (路由表)

route 用于查看和修改 Linux 的路由表。

执行：ip route

可能看到：default via 192.168.1.1 dev eth0

以及：192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.20

  •     第一条表示默认路由：当目标地址没有更具体的路由匹配时，数据包交给 192.168.1.1，通过 eth0 发出。

  •     第二条表示 192.168.1.0/24 是一个直连网络，Linux 可以通过 eth0 直接访问这个网络。

例如你的 Kali 地址是 192.168.1.20/24，现在访问 Ubuntu 192.168.1.30。

Linux 首先根据路由表判断：192.168.1.30 属于 192.168.1.0/24。

因此不需要把数据包交给默认网关，而是直接通过 eth0 发送。随后，如果还不知道 192.168.1.30 的 MAC 地址，就会进入你之前学习过的 ARP 过程。

如果访问的是 8.8.8.8，它不属于 192.168.1.0/24，于是 Linux 使用：

default via 192.168.1.1

把数据包交给默认网关。

这就是 ip route 与你之前学习的路由原理之间的直接联系。

其中一个非常实用的命令是：

ip route get 8.8.8.8

它可以让内核直接告诉你：

如果现在访问 8.8.8.8，我应该从哪个接口出去、使用哪个源 IP、交给哪个下一跳。

这比单纯查看整个路由表更加适合故障分析。

1.1.4 ip neigh （ARP/邻居表）

neigh 用于查看 Linux 的邻居表。在 IPv4 网络中，它主要对应 ARP 缓存。

执行：ip neigh

可能得到类似：192.168.1.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE

这意味着 Kali 已经知道：192.168.1.1 → aa:bb:cc:dd:ee:ff

也就是：IP 地址 → MAC 地址之间的对应关系。这与你之前在 Wireshark 中学习的 ARP 请求和响应完全对应。

例如 Kali 想访问 192.168.1.30，但邻居表中没有这个地址，Linux 就可能通过 ARP 广播询问：

“谁是 192.168.1.30？”

Ubuntu 回复自己的 MAC 地址之后，Linux 才能建立相应的邻居记录。

因此，当你发现：

IP 地址配置正确、接口也 UP，但是局域网内仍然无法通信。

就可以进一步使用 ip neigh 检查邻居状态。

1.1.5 ip 中几个常见的通用选项

除了这些对象之外，ip 还存在一些经常与对象组合使用的选项。

-4 表示只处理 IPv4。例如 ip -4 addr。

-6 表示只处理 IPv6。例如 ip -6 addr。

-s 表示显示统计信息。例如 ip -s link 可以看到接口的收发数据包、字节数、错误数等统计。

-d 表示显示更加详细的网络接口信息，在查看虚拟接口、隧道接口等特殊网络设备时比较有用。

-br 表示使用简洁的 brief 输出。例如 ip -br addr 可以快速得到类似“接口名称 + 状态 + IP 地址”的信息，非常适合日常查看。

1.2 SS 命令

    ss 是 Linux 系统中用于查看 Socket 网络连接状态和监听状态的工具，全称通常解释为 Socket Statistics。它属于 iproute2 工具集，与前面学习的 ip 命令属于同一套现代 Linux 网络工具体系。

如果说 ip 主要用于观察主机的网络接口、IP 地址、路由和邻居关系，那么 ss 更关注的是：

当前主机上的网络通信端点，以及哪些进程正在通过网络进行通信。

对于网络安全而言，ss 是非常重要的主机网络分析工具。进行 Linux 主机安全检查、应急响应、恶意进程排查时，经常需要通过 ss 判断当前系统开放了哪些端口、哪些端口正在监听、哪些连接已经建立，以及这些连接属于什么协议。

1.2.1 ss 使用方式

最基本的用法是：ss

    它可以查看当前系统中的 Socket （ 是Linux 中进程进行网络通信的端点和接口，用于通过 TCP、UDP 等协议收发数据。）信息。但直接使用时输出可能比较庞杂，因此实际分析中经常配合参数进行筛选。

最重要的几个参数是：

参数 含义
-t TCP
-u UDP
-l Listening，只查看监听 Socket
-n 不解析域名和服务名称，直接显示数字
-p 显示对应进程
-a 显示所有 Socket，包括监听和非监听
-4 只查看 IPv4
-6 只查看 IPv6
-s 显示 Socket 汇总统计
-r 尝试解析地址

这些参数可以组合使用，例如 ss -tulnp 。这里不要把它理解成一个固定命令，而应该理解成：协议类型 + 状态 + 显示方式 + 进程信息 这几个维度自由组合。

1.2.2 查看 TCP 连接

执行：ss -t表示查看 TCP Socket。如果系统当前存在 TCP 连接，可能看到类似：

ESTAB 0 0 192.168.1.20:45678 192.168.1.30:22

这里最重要的是理解几个字段。

  • 192.168.1.20:45678 是本地主机的地址和端口。

  • 192.168.1.30:22 是远程主机的地址和端口。

ESTAB 表示 TCP 连接已经建立。因此，如果 Kali 正通过 SSH 连接 Ubuntu：Kali:45678 → Ubuntu:22那么 ss 可以直接观察到这条连接。这与你之前学习的 TCP 三次握手直接对应。

1.2.3 查看监听端口

在网络安全中，比 ss -t 更常用的是：ss -l

-l 表示只查看处于 LISTEN 状态的 Socket。例如某台 Ubuntu 服务器可能监听：0.0.0.0:22和 0.0.0.0:8083这意味着系统存在对应的服务，并且正在等待其他主机建立连接。

如果你正在进行你之前的 Ubuntu 靶机实验，那么可以使用：ss -lnt查看 TCP 监听端口。

其中：

-l → 监听状态
-n → 数字形式显示端口
-t → TCP

这样可以快速得到：

这台 Linux 主机当前开放并监听哪些 TCP 端口？

例如发现：0.0.0.0:22意味着 SSH 服务正在 IPv4 的所有本地地址上监听 22 端口。

而如果是：127.0.0.1:8083则意味着 8083 只绑定在本机回环地址上，其他主机通常无法直接连接这个服务。

这在你之前排查“Ubuntu 的 8083 端口为什么访问不了”时就非常有用。

1.2.4 查看 UDP

TCP 和 UDP 的 Socket 是不同的，因此查看 UDP 时需要使用：ss -u

例如：ss -lun

表示：UDP + Listening + Numeric

也就是查看当前主机正在监听的 UDP 端口。

例如 DNS、DHCP 等服务经常涉及 UDP，因此进行 Linux 网络排查时不能只关注 TCP。

1.2.5 查看端口对应的进程

这是网络安全分析中非常重要的功能。

使用：ss -lntp

其中 -p 表示显示使用这个 Socket 的进程。

例如可能看到：LISTEN ... 0.0.0.0:22 ... users:(("sshd",pid=1234,fd=3))

这时候你就不仅知道：

22 端口开放。

还知道：

22 端口由 sshd 进程监听。

这就把网络层面的端口和操作系统层面的进程联系起来了。在安全分析中，这一点非常重要。

例如你发现一台服务器监听了一个陌生的高位端口 49152，那么仅仅知道“49152 开放”还不够。

可以进一步通过 ss -lntp 判断：

哪个进程 → 哪个 PID → 哪个监听端口

然后再结合 ps、/proc、lsof、systemctl、journalctl 等工具继续分析。

这就是典型的 Linux 主机安全排查思路。

1.2.6 ss -a：查看全部 Socket

-a 表示查看所有 Socket，而不是只查看监听状态。

例如：ss -ant可以查看全部 TCP Socket。

这时候除了 LISTEN，还可能看到：

ESTAB

TIME-WAIT

SYN-SENT

SYN-RECV

CLOSE-WAIT

等 TCP 状态。

这些状态与你之前学习的 TCP 状态机存在直接关系。

例如：

SYN-SENT

表示本机已经发送 SYN，正在等待对方响应。

SYN-RECV

表示本机收到了 SYN，并且已经发送 SYN-ACK，等待最终 ACK。

ESTAB

表示 TCP 连接已经建立。

TIME-WAIT

表示连接关闭后进入等待状态，用于保证旧连接中的延迟报文不会干扰新的连接。

因此，ss 不只是“查端口”，它实际上可以作为观察 Linux TCP 状态机运行情况的工具。

1.2.7 ss -s（查看 Socket 统计）

ss -s 会提供当前系统 Socket 的汇总统计。例如可以看到 TCP、UDP 等 Socket 的数量以及 TCP 各状态的大致分布。它适合快速判断系统当前网络连接规模。

    例如在服务器异常时，如果发现：

大量 TCP 连接处于 TIME-WAIT、SYN-RECV 或其他异常状态，那么可以进一步结合日志、进程和抓包工具进行分析。

这里要注意：

单独看到某种 TCP 状态，并不能直接证明系统遭受攻击。

它只是一个网络状态证据，需要结合连接来源、时间分布、业务行为以及其他日志进行判断。

1.2.8 ss 与 netstat 的关系

你在一些旧的 Linux 教程中可能会看到：

netstat

它曾经是 Linux 中非常常用的网络状态查看工具。

现在 Linux 环境通常更推荐使用 ss。

两者功能存在较大重叠，例如：

netstat -tulnp

与：

ss -tulnp

都可以用于查看 TCP/UDP 监听端口以及相关进程。

因此你学习 Linux 时可能仍然会遇到 netstat，但当前应该把 ss 作为主要工具，而不是把两个命令当成完全不同的知识体系。

1.2.9 从网络安全角度理解 ss

对于安全运营、安全分析和应急响应方向，ss 最重要的价值可以概括成三个问题：

第一：系统开放了什么？

通过 ss -lntup 等组合，可以观察 TCP/UDP 监听端口。

第二：系统正在连接什么？

通过 ss -antup 等方式，可以观察当前建立的网络连接及相关进程。

第三：是谁在通信？

通过 -p 获取进程信息，再结合 PID、ps、/proc 等进一步定位具体程序。

因此，一个非常典型的 Linux 主机网络分析过程是：

端口 → Socket → IP/端口 → 连接状态 → 进程 → 服务 → 日志

这比单纯记住“ss 是查看端口的命令”更加重要。

你目前学习 ss，建议首先熟练掌握 ss -lntup、ss -antup、ss -s，同时真正理解 LISTEN、ESTAB、SYN-SENT、SYN-RECV、TIME-WAIT、CLOSE-WAIT 等状态。这样它才能与你已经学过的 TCP 三次握手、四次挥手、Linux 网络接口和路由真正串起来。

1.3 ping 命令

ping 是 Linux 中用于测试主机之间网络层可达性的基础工具。它通过发送 ICMP Echo Request，等待目标主机返回 ICMP Echo Reply，以判断目标是否能够在当前网络路径上对 ICMP 请求作出响应。

对于网络安全学习而言，ping 最重要的意义不是“测试网络通不通”，而是帮助你理解：IP 层是否存在基本的双向通信能力。

它与前面学习的 ip、ss 处于不同层次：

  • ip：观察和配置本机网络状态；

  • ping：验证到某个 IP 的网络层通信；

  • ss：观察 TCP/UDP Socket 和连接状态。

因此，ping 是一个非常典型的网络连通性诊断工具。

1.3.1 ping 的工作原理

例如 Kali 执行：ping 192.168.1.100

Kali 会向 192.168.1.100 发送 ICMP Echo Request。

如果目标主机正常接收并响应，就会返回 ICMP Echo Reply。

终端可能显示：64 bytes from 192.168.1.100: icmp_seq=1 ttl=64 time=0.5 ms

这里几个字段值得理解。

  • icmp_seq=1 表示这是第 1 个 ICMP 请求，用于区分连续发送的不同数据包。

  • ttl=64 是 IP 数据包中的 TTL（Time To Live）字段。它用于限制数据包经过路由器的最大跳数。每经过一个三层路由设备，TTL 通常减 1。

  • time=0.5 ms 表示从发送请求到收到响应所经历的往返时间，即 RTT（Round-Trip Time）。

因此，ping 不只是告诉你“通不通”，还能够提供一定的延迟、丢包和路径稳定性信息。

1.3.2 ping 常用参数

ping 的参数主要用于控制发送方式、数量、时间间隔以及协议版本。

最常用的是：

参数 作用 示例
-c 指定发送次数 ping -c 4 192.168.1.100
-i 指定发送间隔 ping -i 0.5 192.168.1.100
-W 设置等待响应的超时时间 ping -W 2 192.168.1.100
-s 指定 ICMP 数据部分大小 ping -s 1000 192.168.1.100
-4 使用 IPv4 ping -4 example.com
-6 使用 IPv6 ping -6 example.com
-q 只显示最终统计结果 ping -q -c 4 192.168.1.100

在 Linux 中，直接执行 ping 192.168.1.100 通常会持续发送，直到你使用 Ctrl+C 停止。

如果只想测试四次，更适合：

ping -c 4 192.168.1.100

最终会得到类似：

4 packets transmitted, 4 received, 0% packet loss

这部分统计信息在网络故障排查中很有价值。

1.3.3 ping 与 ARP 的关系

假设 Kali 和 Ubuntu 位于同一个局域网：

Kali：192.168.1.20

Ubuntu：192.168.1.100

Kali 执行：

ping 192.168.1.100

在真正发送 ICMP 数据之前，如果 Kali 不知道 192.168.1.100 对应的 MAC 地址，它首先需要通过 ARP 获取目标 MAC。

因此你可能在 Wireshark 中看到：

ARP Request

↓

ARP Reply

↓

ICMP Echo Request

↓

ICMP Echo Reply

所以：

ARP 负责解决“这个 IP 对应哪个二层地址”，ICMP 负责进行网络层的连通性测试。

这也是为什么你之前学习的 ARP 和现在的 ping 可以自然地联系起来。

1.3.4 ping 成功到底意味着什么

假设：ping 192.168.1.100

能够正常收到 Echo Reply。

它只能说明：

从当前主机到目标主机的 ICMP 通信能够正常完成。

不能因此直接推出：

“目标的 80 端口可以访问。”

例如 Ubuntu：192.168.1.100

能够被 Kali ping 通，但是：192.168.1.100:8083仍然可能无法访问。

这正好与你刚才排查 sqli-labs 的问题对应。

ping 测试的是：IP 层 → ICMP

而访问 8083 测试的是：TCP → 8083 → Docker → 容器服务

所以完全可能出现：ping 成功，但 TCP 8083 失败。

反过来也一样，某些服务器可能禁止 ICMP，但 TCP 80、443 等服务完全正常。因此：

ping 失败不能直接证明目标主机离线。

1.3.5 ping 失败时如何分析

常见情况包括：

Destination Host Unreachable

    通常意味着当前系统或者中间设备认为目标不可达。例如路由不存在、邻居解析失败等。

Request timeout

    表示在规定时间内没有收到 Echo Reply。但原因可能很多，包括网络丢包、目标不响应 ICMP、防火墙过滤或者路由问题。

Network is unreachable

    则更加直接，说明本机当前没有找到可以到达目标网络的有效路径。此时应该首先检查：

ip addr 和： ip route

这就是为什么前面学习 ip 非常重要。

例如：

ping 失败

↓

查看 ip addr

↓

确认本机 IP

↓

查看 ip route

↓

确认目标应该从哪个接口、通过哪个网关出去

↓

必要时查看 ip neigh

↓

再进一步使用 tcpdump / Wireshark 分析实际数据包。

这样，ping 就不再是一个孤立的命令，而成为网络故障排查链中的一个环节。

1.3.6 ping 在网络安全中的意义

在安全运营和应急响应中，ping 经常作为最基础的连通性验证手段。

例如发现一台服务器无法访问，可以先判断：

主机是否具有 IP 配置？

通过 ip addr。

是否存在到目标的路由？

通过 ip route。

目标是否能够响应 ICMP？

通过 ping。

TCP 服务是否能够建立连接？

通过 ss、nc 等工具。

实际数据包有没有到达？

通过 tcpdump 或 Wireshark。

这实际上形成了一套从网络层到传输层的排查逻辑：

IP 配置 → 路由 → ICMP → TCP → 应用服务

对于你目前的学习进度，ping 需要真正掌握的不是大量参数，而是三个核心概念：

ICMP Echo Request / Echo Reply

RTT、TTL、丢包率

“Ping 通”不等于“服务端口可用”

这三个概念掌握之后，ping 作为 Linux 网络基础工具的学习就基本达到要求。

1.4 traceroute 命令

traceroute 是 Linux 中用于 探测从本地主机到目标主机之间经过哪些三层网络设备（Hop） 的诊断工具。

如果 ping 回答的是：

“我能不能到达目标？”

那么 traceroute 进一步回答：

“从我到目标，中间经过了哪些路由器？”

因此，在你的网络安全学习体系中，traceroute 应该与前面学习的 IP、路由、ICMP、TTL 联系起来理解，而不是单纯记住它是“查看路径”的命令。

1.4.1 traceroute 的核心原理

traceroute 最核心的机制是 TTL（Time To Live）。

假设 Kali 要访问某个目标：

Kali → 路由器 A → 路由器 B → 路由器 C → 目标

如果 Kali 发送一个 TTL 为 1 的 IP 数据包，那么数据包经过第一个路由器 A 时，TTL 会减 1，变成 0。路由器发现 TTL 已经耗尽，就不会继续转发，而是向 Kali 返回：

ICMP Time Exceeded

于是 Kali 知道：

第 1 跳是路由器 A。

然后 traceroute 再发送 TTL 为 2 的数据包。

这一次：

Kali → A → B

到达 B 时 TTL 才耗尽，因此 B 返回 ICMP Time Exceeded。

于是 Kali 知道：

第 2 跳是路由器 B。

继续增加 TTL：

TTL=3 → 找到第 3 跳

TTL=4 → 找到第 4 跳

最终到达目标。

因此，traceroute 的基本逻辑可以概括为：

逐渐增加 TTL，通过中间路由器返回的 ICMP Time Exceeded 消息，推断数据包经过的路径。

这就是 traceroute 最核心的原理。

1.4.2 一个实际例子

例如 Kali 执行：traceroute 8.8.8.8

可能看到类似：

1 192.168.1.1

2 10.0.0.1

3 100.x.x.x

4 ...

这里每一行代表一个 Hop（跳）。

第一跳通常可能是你的默认网关。

如果你的 Kali 是：

192.168.1.20

路由表中存在：

default via 192.168.1.1

那么第一跳很可能就是：

192.168.1.1

这就是为什么你刚刚学习的 ip route 对理解 traceroute 很重要。

ip route 告诉你：

本机准备把数据包交给谁。

traceroute 则进一步观察：

数据包离开本机以后，又经过了哪些路由器。

1.4.3 traceroute 常用参数

不同 Linux 版本的 traceroute 参数可能存在一些差异，但 Kali 中常见的参数主要包括：

参数 作用 示例
-n 不进行 DNS 解析 traceroute -n 8.8.8.8
-4 使用 IPv4 traceroute -4 example.com
-6 使用 IPv6 traceroute -6 example.com
-m 设置最大 TTL / 最大跳数 traceroute -m 20 8.8.8.8
-w 设置等待响应时间 traceroute -w 2 8.8.8.8
-q 每一跳发送多少个探测包 traceroute -q 3 8.8.8.8
-I 使用 ICMP Echo 探测 traceroute -I 8.8.8.8
-T 使用 TCP 探测 traceroute -T -p 443 example.com
-U 使用 UDP 探测 traceroute -U 8.8.8.8

其中非常值得你注意的是 -I、-T 和 -U。

因为 traceroute 并不只有一种探测方式。

1.4.4 为什么 traceroute 有 UDP、ICMP 和 TCP

传统 Unix/Linux traceroute 经常使用 UDP 探测包。

但现实网络中，防火墙可能会对不同协议采取不同的过滤策略。

因此：traceroute -I 8.8.8.8使用 ICMP Echo 进行探测。

而：

traceroute -T -p 443 example.com

则使用 TCP 探测，并把目标端口设置为 443。

这在网络安全分析中非常有意义。

例如某个网络禁止普通 ICMP，但允许 HTTPS：

ping → 失败

并不意味着：

网络 → 不通

这时可以尝试 TCP 443 的路径探测。

所以需要形成一个非常重要的认识：

不同探测协议经过网络设备时，可能得到不同的结果。

1.4.5 为什么中间有 * * *

你使用 traceroute 时非常可能看到：

1 192.168.1.1

2 * * *

3 10.0.0.1

这里的 * 并不意味着第二跳一定不存在。

它更准确地表示：

在规定时间内，没有收到对应探测包所期待的响应。

原因可能包括：

  • 路由器不返回 TTL Exceeded；

  • 防火墙过滤 ICMP；

  • 中间设备限制 traceroute；

  • 网络设备对探测包进行速率限制；

  • 返回数据包丢失；

  • 网络本身存在丢包。

因此：

* * * ≠ 该路由器不存在。

这和刚才讲 ping 时的原则一样：没有收到响应，不等于目标一定不存在。

1.4.6 traceroute 与 TTL 的关系

假设：Kali → R1 → R2 → R3 → Server

第一次探测：TTL = 1

R1 收到后 TTL 变为 0，于是返回 ICMP Time Exceeded。

第二次：TTL = 2

R1 将 TTL 减 1，然后转发给 R2。

R2 将 TTL 再减 1，变成 0，于是 R2 返回 ICMP Time Exceeded。

第三次：

TTL = 3

最终在 R3 处耗尽。

所以：

traceroute 本质上是在利用 TTL 的逐跳递减特性，把原本不可见的网络路径暴露成一组可观察的 Hop。

这是你学习网络协议时应该真正理解的核心。

1.3.7 traceroute 与 ping、ip route 的区别

现在把三个命令放在一起看，会非常清楚。

  • ip route

关注的是：

Linux 本机如何做路由决策。

例如：

default via 192.168.1.1 dev eth0

告诉你本机应该把未知目标的数据包交给 192.168.1.1。

  • ping

关注的是：

目标是否能够通过 ICMP 对我的请求进行响应，以及 RTT 和丢包情况。

  • traceroute

关注的是：

数据包从本机到目标之间经过了哪些三层 Hop。

因此可以形成：

ip route → 本机决定怎么走

↓

traceroute → 实际路径上看到了什么

↓

ping → 目标是否能够响应

当然，这三个工具观察的是不同维度，不能简单认为 traceroute 就是 ping 的“升级版”。

1.3.8 网络安全中的价值

在安全运营和应急响应中，traceroute 可以辅助判断网络路径、路由异常和网络边界。例如一台服务器突然无法访问某个外部服务，可以先使用 ping 判断是否有基本的 ICMP 响应，再用 traceroute 观察路径在哪一跳开始发生异常。

如果：

1～5 跳正常 第 6 跳开始全部 *

这只能说明从第 6 跳开始无法继续获得 traceroute 所期待的响应，并不能直接断定第 6 跳就是故障点。

如果结合 ip route、ss、tcpdump 以及实际 TCP 连接测试，就能够进一步判断问题究竟发生在：

本机 → 默认网关 → ISP → 中间路由 → 防火墙 → 目标网络 → 目标主机

哪一个范围。

另外，在安全测试和网络资产分析中，traceroute 还可以帮助理解目标网络的拓扑边界、路由路径以及网络设备响应特征，但它获得的路径只是基于探测响应推断出的可见路径，并不一定等于真实完整拓扑。

1.3.9 验收要求

对于目前的 Linux 网络学习阶段，traceroute 不需要把所有参数全部背下来。真正需要掌握的是：

第一，理解 TTL 逐跳递减。

第二，理解 ICMP Time Exceeded 的作用。

第三，能够阅读每一个 Hop。

第四，理解 * * * 的含义，知道它不能直接等价于“路由器不存在”。

第五，知道 UDP、ICMP、TCP traceroute 的区别。

第六，能够把 ip route → traceroute → ping 联系起来。

如果这部分掌握，那么你前面学习的 IP、路由、TTL、ICMP、ARP、TCP 就开始真正形成一个完整的网络诊断体系了。

1.5 Curl 命令

curl 是 Linux 中用于进行网络请求与网络数据传输的命令行工具。与前面学习的 ping、traceroute 不同，curl 主要工作在应用层，最常用于 HTTP/HTTPS 请求，也可以处理 FTP、SMTP 等协议。

对于网络安全学习而言，curl 的核心价值不是“下载文件”，而是直接构造、发送、观察网络请求。后续学习 HTTP、Web 安全、API、安全测试时都会大量使用。

1.5.1 curl 的基本结构

基本语法为：

curl [选项] URL

例如：curl http://192.168.1.100:8083

这条命令会向 192.168.1.100 的 8083 端口发送一个 HTTP 请求。

最简单的：curl https://example.com

默认执行的是 HTTP GET 请求，并把服务器返回的响应体直接输出到终端。

因此你可以把一次 curl 请求理解为：

DNS → TCP → TLS（HTTPS）→ HTTP Request → HTTP Response

这正好可以把你之前学习的网络知识串起来。

1.5.2 curl 所能携带的主要参数

curl 的参数非常多，但网安学习阶段不需要全部记忆，首先掌握下面这些。

-v：查看详细通信过程

这是网络安全学习中非常重要的参数：

curl -v http://example.com

它会显示类似：

> GET / HTTP/1.1
> Host: example.com
> User-Agent: curl/...

以及服务器返回的：

< HTTP/1.1 200 OK
< Content-Type: text/html

因此：

curl 默认主要看响应内容，curl -v 可以观察请求与响应的关键元数据。

对于你目前正在学习的 HTTP，这个参数应该重点掌握。

-I：只发送 HEAD 请求

curl -I https://example.com

用于查看 HTTP 响应头，而不获取完整响应体。

例如可以观察：

HTTP/1.1 200 OK
Server: nginx
Content-Type: text/html
Set-Cookie: ...

这对于判断服务器、Cookie、缓存、重定向等非常有用。

注意：-I 默认使用的是 HEAD，不是 GET。

-i：把响应头和响应体一起显示

curl -i http://example.com

与 -I 不同：

  • -I：发送 HEAD，请求响应头

  • -i：正常发送 GET 等请求，但把响应头也显示出来

-X：指定 HTTP 方法

例如：

curl -X GET http://example.com

curl -X POST http://example.com/login

curl -X PUT http://example.com/user/1

curl -X DELETE http://example.com/user/1

不过实际使用中，不建议把 -X 当成所有请求的必需参数。例如 POST 可以直接使用 -d，curl 会自动使用 POST。

-H：添加 HTTP Header

这是 Web 安全中非常重要的参数。

例如：

curl -H "User-Agent: Mozilla/5.0" http://example.com

添加 Authorization：

curl -H "Authorization: Bearer TOKEN" http://example.com/api/user

添加 Cookie：

curl -H "Cookie: session=abc123" http://example.com/

因此你之前学习的：

Cookie、Session、Token、JWT、Authorization

都可以通过 curl 手动构造请求进行验证。

-d：发送 POST 数据

例如：

curl -d "username=admin&password=123456" http://example.com/login

默认情况下，curl -d 会使用 POST。

它通常对应：Content-Type: application/x-www-form-urlencoded

如果服务器 API 接收 JSON，可以：

curl -H "Content-Type: application/json" -d '{"username":"admin","password":"123456"}' http://example.com/login

这对后面学习 REST API、认证机制以及 Web 安全测试非常重要。

-o：保存响应到文件

curl -o result.html http://example.com

将响应保存为 result.html。

-O：按照 URL 中的文件名保存

curl -O https://example.com/test.zip

例如 URL 最后是 test.zip，curl 就保存成 test.zip。

-L：跟随重定向

例如服务器返回：

HTTP/1.1 302 Found
Location: /login

默认情况下 curl 不一定继续访问 /login。

使用：curl -L http://example.com

就会继续跟随 Location。

Web 登录流程中经常遇到：

/ → 302 → /login → 200

所以 -L 很常用。

-k：忽略 TLS 证书验证

curl -k https://192.168.1.100

用于测试自签名证书等环境。

但需要明确：

-k 是关闭证书验证，不是关闭 HTTPS 加密。

实际安全环境中不应该无条件使用。

-s：静默模式

curl -s https://example.com

减少进度信息输出，脚本中比较常用。

-w：输出请求统计信息

例如：

curl -w "%{http_code} %{time_total}\n" -o /dev/null -s https://example.com

可以得到类似：

200 0.183421

分别表示 HTTP 状态码和总请求时间。

这个参数在批量检测、日志分析、服务监控中很有价值。

1.5.3 curl 与前面学习的工具之间的关系

现在已经学习了 ip、ss、ping、traceroute，可以把它们放进同一套网络诊断体系：

工具 主要观察对象
ip 本机网络配置、接口、IP、路由、ARP 邻居
ss 本机 Socket、TCP/UDP、监听端口、连接状态
ping IP 层连通性、ICMP、RTT、丢包
traceroute 到目标的三层路径
curl 应用层 HTTP/HTTPS 请求与响应

例如你之前 Ubuntu 的 8083 问题，就可以形成完整诊断链：

ip addr → 本机 IP 是否正确

ip route → 路由是否正确

ping Ubuntu_IP → IP 层是否可达

ss -lntp | grep 8083 → 8083 是否监听

curl http://127.0.0.1:8083 → HTTP 服务是否真正能够响应

而你之前已经得到：0.0.0.0:8083 -> docker-proxy -> container:80

但容器内部 ss -lnt 没有发现 80 端口监听，因此 curl 出现：

Recv failure: Connection reset by peer

这就是 curl 在实际故障排查中的价值：它能够把“端口存在”和“应用能够正确处理 HTTP 请求”区分开。

1.5.4 curl 在网络安全中的核心用途

你后面学习 Web 安全时，curl 会成为基础工具之一。

例如检查响应头：

curl -I https://example.com

检查完整 HTTP 交互：

curl -v https://example.com

手动发送 Cookie：

curl -H "Cookie: session=xxxx" https://example.com/user

手动发送 JWT：

curl -H "Authorization: Bearer eyJ..." https://example.com/api/user

发送 JSON：

curl -H "Content-Type: application/json" -d '{"id":1}' https://example.com/api/user

观察重定向：

curl -I https://example.com

观察 TLS：

curl -v https://example.com

因此，curl 本质上是一个命令行 HTTP 客户端，同时也是学习和验证 Web 协议的重要实验工具。

按照你目前的学习路线，下一阶段你不需要把 curl 的所有参数全部背下来，应该重点达到：

能够使用 curl 构造 GET、POST、JSON、Cookie、Authorization 请求；能够读取 HTTP 状态码、响应头、响应体、重定向；能够用 -v 分析一次 HTTP/HTTPS 请求的基本过程。

这部分掌握后，就可以继续进入更贴近安全分析的 nc（netcat），然后把 curl + nc + ss + tcpdump/Wireshark 串起来。

1.6 dig命令

dig（Domain Information Groper）是 Linux 中用于查询 DNS（Domain Name System）信息的命令行工具。它主要用于直接向 DNS 服务器发送 DNS Query，并解析返回的 DNS Response。

对于网络安全学习，dig 的重要性高于单纯的域名解析工具。你已经通过 Wireshark 学习过 DNS 请求/响应，因此现在学习 dig 的目的，是把之前看到的 DNS 报文转换成可控、可重复的命令行查询。

基本语法：dig [选项] [@DNS服务器] 域名 [查询类型]

例如：dig example.com

表示查询 example.com 的 DNS 信息。

1.6.1 dig 能查询什么

DNS 并不只有 IP 地址。最常见的记录类型包括：

类型 含义
A 域名 → IPv4
AAAA 域名 → IPv6
CNAME 别名 → 规范域名
MX 邮件服务器
NS 权威 DNS 服务器
TXT 文本记录，常用于 SPF、验证等
SOA DNS 区域的权威起始信息
PTR IP → 域名，反向解析

例如：

dig example.com A

查询 IPv4 地址。

dig example.com AAAA

查询 IPv6 地址。

dig example.com MX

查询邮件服务器。

dig example.com NS

查询该域名的 DNS 权威服务器。

因此，dig 不只是“查 IP”，而是用于检查 DNS 数据本身。

1.6.2 dig 输出应该怎么看

执行：

dig example.com

通常会看到几个重要部分：

  • QUESTION SECTION

表示你向 DNS 服务器提出了什么问题。

例如：

example.com. IN A

含义是：

  • example.com.：查询的域名

  • IN：Internet 类

  • A：查询类型

然后是：

  • ANSWER SECTION

这是 DNS 服务器返回的答案。

例如：

example.com. 300 IN A 93.184.216.34

其中：

  • example.com.：域名

  • 300：TTL

  • IN：Internet

  • A：记录类型

  • 93.184.216.34：IPv4 地址

下面还可能出现：

AUTHORITY SECTION

表示 DNS 服务器提供的权威信息。

ADDITIONAL SECTION

表示额外提供的信息，例如 NS 对应的地址。

最后的：

Query time: 20 msec
SERVER: 192.168.1.1#53

分别表示：

DNS 查询耗时和实际使用的 DNS 服务器。

这一点在排查 DNS 问题时非常重要。

1.6.3 指定 DNS 服务器

这是 dig 最值得掌握的功能之一。

语法：

dig @DNS服务器 域名

例如：

dig @8.8.8.8 example.com

表示：

不要使用系统默认 DNS，而是直接向 8.8.8.8 查询。

也可以：

dig @1.1.1.1 example.com

然后比较不同 DNS 服务器返回的结果。

在安全分析和故障排查中，这非常有价值，因为：

不同 DNS 服务器可能由于缓存、地域、DNS 污染、配置、分流等原因返回不同结果。

例如：

dig @192.168.1.1 example.com
dig @8.8.8.8 example.com

如果结果不同，就需要进一步判断是缓存、DNS 配置、解析策略还是其他网络因素。

1.6.4 查询指定记录类型

例如：

dig example.com A

查询 IPv4。

dig example.com AAAA

查询 IPv6。

dig example.com MX

查询邮件系统。

dig example.com NS

查询 DNS 权威服务器。

dig example.com TXT

查询 TXT。

其中 TXT 在安全分析中比较值得关注，因为它可能包含：

SPF、DKIM、域名验证、第三方服务验证等信息。

例如一个企业域名可能存在：

TXT "v=spf1 ..."

这说明 DNS 不只是网络基础设施，也可能包含大量安全配置和基础设施信息。

1.6.5 反向 DNS 查询

如果你已经有一个 IP，可以查询 PTR：

dig -x 8.8.8.8

这里的 -x 表示进行反向 DNS 查询。

逻辑与普通 DNS 不同：

普通：

域名 → A/AAAA → IP

反向：

IP → PTR → 域名

需要注意，并不是所有 IP 都存在 PTR 记录。

因此：

dig -x IP

没有结果，并不意味着这个 IP 不存在或者不可用。
六、只看最终答案

完整 dig 输出信息比较多，可以使用：

dig +short example.com

例如只得到：

93.184.216.34

查询 MX：

dig +short example.com MX

查询 NS：

dig +short example.com NS

+short 很适合脚本和批量处理。
七、追踪 DNS 委派过程

dig 中一个非常重要的参数：

dig +trace example.com

它会尝试从 DNS 根开始，逐步追踪：

Root → TLD → Authoritative DNS → 最终记录

例如逻辑上：

.
↓
.com
↓
example.com 的权威 DNS
↓
example.com A

这和你之前学习的 traceroute 完全不是一回事。

traceroute：

追踪 IP 网络路径。

dig +trace：

追踪 DNS 委派/解析过程。

这个区别必须明确。
八、dig 与 Wireshark 的对应关系

你之前已经学习过 DNS 抓包，因此可以直接把两者对应起来。

执行：

dig example.com A

实际上会产生 DNS Query。

典型过程：

应用程序 → DNS Resolver → UDP/TCP 53 → DNS Response

如果使用 Wireshark 抓包，你可以看到：

Standard query A example.com

然后：

Standard query response A example.com

因此现在可以进行一个非常适合你的实验：

在 Kali 执行：

dig @8.8.8.8 example.com A

同时 Wireshark 过滤：

dns

然后观察：

dig 参数 → DNS Query → UDP → IP → 网络 → DNS Response → dig 输出

这样你之前学习的 DNS 抓包知识就真正和 Linux 工具结合起来了。
九、dig 在网络安全中的作用

在安全运营、应急响应和网络分析中，dig 经常用于：

DNS 故障排查

例如判断：

域名 → IP

是否正常。

基础设施分析

通过：

A / AAAA / CNAME / MX / NS / TXT

了解域名相关基础设施。

DNS 异常分析

比较不同 DNS Resolver 的结果，例如：

dig @DNS1 example.com

与：

dig @DNS2 example.com

事件响应

当日志中出现可疑域名时，可以查询：

A、AAAA、CNAME、NS、TXT、SOA 等记录，辅助判断其 DNS 配置和关联基础设施。

但需要注意：DNS 查询结果只是某一时刻 DNS 系统对外提供的数据，不能仅凭一条 A 记录判断某个服务器的真实归属或恶意性。
十、你现在需要掌握到什么程度

按照你目前的网络安全学习进度，dig 不需要把所有参数背下来。验收标准应该是：

  1. 知道 dig 是 DNS 查询工具，而不是普通的“域名查 IP”工具。

  2. 能解释 A / AAAA / CNAME / MX / NS / TXT / SOA / PTR。

  3. 能使用 dig domain A、dig domain MX、dig domain NS。

  4. 能使用 dig @DNS-server domain 指定 DNS 服务器。

  5. 能使用 dig -x IP 做反向解析。

  6. 能使用 dig +short domain 获取简洁结果。

  7. 能使用 dig +trace domain 理解 DNS 委派链。

  8. 能把 dig 输出与 Wireshark 中的 DNS Query/Response 对应起来。

到这里，你的工具链已经开始形成：

ip → 本机网络配置
ss → Socket/端口/连接
ping → IP 层连通性
traceroute → IP 路径
curl → HTTP/HTTPS 应用层通信
dig → DNS 查询与分析

这几个工具实际上已经覆盖了你进行一次基础网络故障分析时最常见的几个层面。

Command

藏匿身份

shred

    shred 是 Linux 中用于安全删除文件的工具，在网络安全中主要用于降低已删除敏感文件被恢复的可能性。普通的 rm 通常只是删除文件的目录项，文件数据可能仍残留在磁盘上，而 shred 会通过多次向文件原有数据区域写入内容来覆盖数据，再删除文件，使数据恢复更加困难，因此常用于安全运维、应急响应后的敏感数据清理以及设备报废前的数据处理。例如 shred -u sensitive.log 表示覆盖并删除指定文件。不过需要注意，现代 SSD 使用闪存管理、磨损均衡和 TRIM 等机制，shred 并不能保证 SSD 上的数据绝对不可恢复，因此高安全要求场景通常需要结合磁盘加密、厂商安全擦除等机制。

正如你在屏幕上的完整输出中看到的，shred 命令有很多选项。在最基本的形式下，语法很简单：

$$
shred
$$

    单独使用时，shred 会删除文件并多次覆盖它——默认情况下，shred 会覆盖四次。一般来说，文件被覆盖的次数越多，就越难恢复，但要记住每次覆盖都需要时间，所以对于非常大的文件，shred 可能会很耗时。

有两个有用的选项可以使用：

        -f 选项会更改文件的权限，以便在需要权限更改时允许覆盖;

        –n 选项则可以让你选择覆盖文件的次数;

举个例子，我们用下面的命令将 /var/log/auth.log 日志文件覆盖 10 次：

$$
shred -f -n 10 /var/log/auth.log.*
$$

    我们需要使用 –f 选项来获得删除认证文件的权限，然后在 –n 选项后跟上想要覆盖的次数。在指定要删除的文件路径之后，我们加上通配符星号，这样不仅会删除 auth.log 文件，还会删除通过 logrotate 创建的其他日志，比如 auth.log.1、auth.log.2 等等。

    一旦你彻底销毁了一个文件，你会看到里面的内容变成了无法理解的乱码。如果安全工程师或取证调查员检查日志文件，他们将发现没有任何用处，因为这些都无法恢复！

Proxychains

Kali Linux 有一个很棒的代理工具叫做 proxychains，你可以设置它来隐藏你的流量。proxychains 命令的语法很简单，如下所示：

$$
proxychains < the command you want proxied > < arguments >
$$

你提供的参数可能会包含一个IP地址。例如，如果你想用proxychains来匿名使用nmap扫描一个网站，你可以输入以下内容：

$$
proxychains nmap -sT -Pn < IP address >
$$

这将通过代理向指定的 IP 地址发送 nmap –sS 隐蔽扫描命令。然后工具会自己构建代理链，所以你不用担心它。
