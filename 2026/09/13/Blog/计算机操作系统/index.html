计算机操作系统

1 Linux 基础

1.1 用户与组管理

1.1.1 标识符命名空间与体系定位

    Linux的访问控制模型建立在离散访问控制（DAC, Discretionary Access Control基础之上，其核心是将每一个主体（进程）与一组数值型标识符绑定：UID（User Identifier）与GID（Group Identifier）。内核在进行权限判定时，比对的对象始终是这组数值，而非用户名字符串——用户名到UID的映射仅存在于用户态的解析层（NSS，见1.1.2），这是理解后续所有安全分析的前提。

    进程凭证（credential） 结构中实际维护四类UID/GID，而非单一值：

凭证类型 内核结构字段 语义
真实UID（RUID） cred->uid 标识发起该进程的真实身份，通常继承自父进程
有效UID（EUID） cred->euid 内核执行权限检查时实际采用的UID，受SUID位影响可与RUID分离
保存UID（SUID，Saved UID） cred->suid 用于特权进程临时降权后恢复原权限，是seteuid()/setuid()语义的基础
文件系统UID（FSUID） cred->fsuid Linux特有扩展，仅用于文件系统操作的权限判定，服务于NFS服务端等场景

GID同样存在RGID/EGID/SGID/FSGID四元结构，语义对称。这一分离机制是su、sudo、SUID可执行文件权限提升/降权行为在内核层面得以实现的基础，也是后续分析SUID二进制安全风险（对应1.2节特殊权限位）的理论前提。

1.1.2 名称解析架构：NSS与身份数据库

    用户名/组名到UID/GID的转换并非硬编码于内核，而是通过名称服务切换（NSS, Name Service Switch） 框架完成，其配置文件为/etc/nsswitch.conf。关键配置项：
passwd: files sss
group: files sss
shadow: files

files表示本地文件（/etc/passwd、/etc/group），sss（SSSD）或ldap表示企业环境中常见的集中式身份源。这一架构解释了为何在接入LDAP/AD的生产主机上，getent passwd的输出会多于/etc/passwd文件本身的内容——安全巡检脚本若仅解析/etc/passwd而不通过getent，将对集中认证环境下的账户产生系统性遗漏，这是编写主机巡检工具时的一个常见盲点。

    PAM（Pluggable Authentication Modules，/etc/pam.d/）与NSS是正交但协同的两套子系统：NSS负责”用户是谁”（身份解析），PAM负责”如何验证身份、账户策略、会话初始化”（认证与授权流程）。二者共同构成账户安全体系的用户态基础设施。

1.1.3 用户分类与UID区间规范

UID区间划分由发行版遵循的规范（结合/etc/login.defs中的UID_MIN/UID_MAX/SYS_UID_MIN/SYS_UID_MAX参数）决定，不同发行版存在差异：

类别 UID区间（RHEL/CentOS/Fedora系） UID区间（Debian/Ubuntu系） 特性
超级用户 0 0 绕过全部DAC检查（CAP_DAC_OVERRIDE等能力集）
系统/服务账户 1–999 1–999（部分保留至99） 通常无交互登录能力，绑定守护进程
普通用户 1000+ 1000+ 交互式登录账户

关键安全命题：UID是唯一的权限判定依据，用户名仅为展示层语法糖。 这意味着系统中允许存在多个用户名映射至同一UID（/etc/passwd不强制UID唯一性，仅由useradd默认行为保证），此为一种经典的持久化与身份混淆手法——攻击者创建形如sys_monitor:x:0:0::/root:/bin/bash的账户，id命令与ls -l的属主展示均会显示为sys_monitor，但其内核权限与root完全等价。这是主机巡检脚本中”UID=0异常账户检测”这一检查项的理论依据，不能仅通过用户名黑名单进行判断。

1.1.4 组模型：主组与附加组

Linux的组隶属关系分为两层，二者在权限判定与文件存储位置上均不同：

  • 主组（Primary Group / Login Group）：记录于/etc/passwd第4字段（GID），进程创建文件时默认赋予的属组即为此值。每个用户有且仅有一个主组。
  • 附加组（Supplementary Group）：记录于/etc/group第4字段的成员列表，一个用户可隶属于零至多个附加组，内核在权限检查时会遍历进程凭证中的supplementary group list（通过getgroups()/setgroups()系统调用维护）。

需特别注意的解析陷阱：若某用户的主组恰为组A，该用户不会出现在/etc/group中组A对应行的成员列表内——因为主组关系仅记录在/etc/passwd，/etc/group的成员列表仅表达附加组关系。因此，编写”查询用户所属全部组”的逻辑（无论是shell脚本还是Python）时，正确做法是调用id -Gn username或Python的grp模块结合pwd模块交叉查询，而非仅grep一次/etc/group。

组切换的会话语义由newgrp命令实现：该命令启动一个新的子shell，将指定组临时提升为该会话的有效主组，用于满足某些工具（如某些版本控制系统）对”当前有效GID”的强依赖，此机制与前述FSGID的存在动机相关。

1.1.5 账户生命周期管理：命令族与底层实现

useradd/usermod/userdel并非直接的系统调用封装，而是用户态工具，其执行过程涉及对多个文件的原子化写入：

受影响文件矩阵：

文件 内容 useradd写入
/etc/passwd 用户基本信息（见1.3节详述） 是
/etc/shadow 密码哈希与账户时效策略 是（初始密码字段为!或*，表示锁定）
/etc/group 组成员关系 是（若指定附加组）
/etc/gshadow 组管理员与组密码（现代系统基本弃用） 是
/etc/login.defs 全局默认策略（UID_MIN、PASS_MAX_DAYS等），仅读取不写入 否
/etc/default/useradd useradd自身的默认参数（默认shell、家目录基路径、账户过期策略等） 否

useradd执行流程要点：UID分配遵循”取UID_MIN至UID_MAX区间内未占用的最小值”原则（除非显式指定-u）；-m触发家目录创建，其内容来自/etc/skel骨架目录的复制；家目录权限模式由/etc/login.defs中的UMASK及USERGROUPS_ENAB策略共同决定。

核心参数语义辨析：
useradd -m -s /bin/bash -g devops -G secteam,docker testuser

参数 语义
-m 创建家目录并从/etc/skel填充初始内容
-s 指定登录shell，写入/etc/passwd第7字段
-g（小写） 指定主组，可为组名或GID
-G（大写） 指定附加组集合，多个组以逗号分隔

usermod的-G与-aG之间存在集合语义上的根本差异，这是运维安全事故的高频诱因之一：

  • usermod -G secteam testuser：将该用户的附加组集合替换（覆盖赋值）为{secteam}，若该用户此前隶属于docker、sudo等组，这些隶属关系将被清除。
  • usermod -aG secteam testuser：-a（append）使操作变为集合并集运算，即新附加组集合 = 原集合 ∪ {secteam}。

从安全审计角度，若巡检脚本发现某高权限组（如sudo、wheel、docker）的成员列表在短时间内发生非预期变化，需要结合审计日志（/var/log/auth.log或journalctl中usermod的调用记录，通常需依赖auditd的execve规则捕获）判断是覆盖操作导致的组关系丢失，还是恶意追加导致的权限扩张，二者的攻击画像完全不同。

1.1.6 面向安全审计的账户异常识别方法论

结合以上理论基础，主机侧账户安全巡检应覆盖以下检查维度（此处为方法论层面，具体实现将在1.7/1.8节的Python脚本中落地）：

  1. UID别名检测：遍历/etc/passwd，标记所有UID为0但用户名非root的记录。
  2. 异常交互式Shell检测：交叉比对UID区间与shell字段——系统账户（UID<1000）却绑定/bin/bash等交互式shell（而非/sbin/nologin或/bin/false）属于配置风险，需与基线（首次巡检建立的正常状态快照）比对以降低误报。
  3. 空密码/弱密码字段检测：解析/etc/shadow第2字段，空字符串表示无密码即可登录（需同时确认PAM配置nullok选项是否被禁用，二者需联合判断，仅查/etc/shadow可能产生误报），详见1.3节。
  4. 高权限组成员基线比对：对sudo/wheel/root等组的成员列表建立时间序列快照，检测非预期变更。
  5. UID重复性检测：/etc/passwd本身不强制UID唯一，多个用户名共享同一UID是需要重点标记的异常模式（对应1.1.3所述的身份混淆手法）。

1.1.7 实验验证方案

为验证以上理论在实际系统中的行为一致性，建议在实验环境中执行以下操作序列并记录内核凭证的实际变化：
# 建立对照组：创建组与用户
groupadd secteam
useradd -m -s /bin/bash testuser
# 验证初始凭证状态（观察RUID/EUID及附加组集合的初始值）
id testuser
# 验证 -G（覆盖语义）与 -aG（并集语义）的行为差异
usermod -G secteam testuser
id testuser # 记录此时的附加组集合

usermod -aG docker testuser 2>/dev/null || groupadd docker && usermod -aG docker testuser
id testuser           # 对比：secteam是否仍然存在于附加组集合中

usermod -G docker testuser
id testuser           # 验证secteam是否已被覆盖清除

# 交叉验证解析层与存储层的一致性
grep testuser /etc/passwd
grep -E "secteam|docker" /etc/group
getent passwd testuser   # 对比files直接读取与NSS解析路径的结果差异

验证要点：id命令输出中uid=、gid=（主组）、groups=（全部组，含主组与附加组的并集展示）三部分应与/etc/passwd、/etc/group的原始记录逐一对应；第三组操作应观察到secteam从附加组集合中消失，以此实证-G的覆盖语义。

1.2 权限体系（rwx与特殊权限位）

1.2.1 权限判定算法：内核层执行流程

Linux文件权限检查发生在VFS（Virtual File System）层，每次访问请求（open()、exec()等系统调用）触发时，内核按以下互斥优先级顺序进行判定，而非”三组权限逐一累加”：

  1. 若进程的EUID（有效UID，见1.1.1）等于文件的属主UID，则应用属主（owner/user）权限位，判定结束。
  2. 否则，若进程的EUID/EGID或附加组集合中任一GID等于文件的属组GID，则应用属组（group）权限位，判定结束。
  3. 否则应用其他（other）权限位。

关键推论：权限判定是排他的，不存在”取并集”的情形。 这意味着一个经典的配置陷阱——文件属主权限为rw-（无x），但属组权限为rwx——对于文件属主本人而言，即使他同时也隶属于该属组，其有效权限仍然是属主位的rw-，因为判定在第1步已经终止，不会继续检查第2步的属组位。这一点在排查”明明加了组权限但用户依然无法执行”类问题时是核心诊断依据，也是安全巡检工具评估”某进程实际可访问权限”时必须精确建模的逻辑，不能简单地做位或运算。

例外情形：CAP_DAC_OVERRIDE能力（Linux Capabilities机制的一部分，root默认持有）使得该进程完全绕过上述三步判定，这是”root可以读写任意文件”这一直觉的精确内核语义来源，也是最小权限原则（通过setcap移除root的部分能力集）在容器安全、服务加固场景中的理论基础。

1.2.2 三元权限位的语义在不同对象类型上的差异

r/w/x对普通文件与目录的语义存在本质差异，这一差异是初学者最常见的理解误区：

权限位 普通文件 目录
r (4) 允许读取文件内容 允许列出目录内条目名称（ls）
w (2) 允许修改文件内容 允许在目录内创建/删除/重命名条目——注意：删除文件的权限取决于其所在目录的w位，而非文件自身的权限位
x (1) 允许将文件作为程序执行，或作为解释器脚本传递给内核的execve() 允许穿越该目录（即以路径的一部分访问其下条目，如cd或访问dir/file），若无x位，即使有r位也无法stat()目录内的具体条目属性

由此可推导出一个反直觉但高频出现的安全场景：某文件权限为----------（属主属组其他全部无权限），只要其父目录对当前用户开放w权限，该用户依然可以删除此文件——这是文件系统层面”删除操作的权限判定对象是目录而非文件本身”这一设计决策的直接后果，也是评估”权限加固是否真正生效”时容易被忽略的一环。

1.2.3 数字与符号表示法的位运算本质

权限模式在内核inode结构中以st_mode字段的低12位存储，可分解为：
特殊位(3 bit) | 属主(3 bit) | 属组(3 bit) | 其他(3 bit)
SUID/SGID/T | rwx | rwx | rwx

    数字表示法（如chmod 755）本质是这12位的八进制编码，每3位一组对应一位八进制数字，r=4、w=2、x=1的取值源于二进制位权（100、010、001）。符号表示法（如chmod u+x,g-w）则是对特定位的增量式（相对）修改，二者在chmod(2)系统调用层面最终都归约为同一个mode_t整数参数。

1.2.4 umask：默认权限的位运算生成机制

新建文件/目录的初始权限并非直接由umask决定，而是通过如下运算：
文件初始权限 = 请求权限 & (~umask)

    其中”请求权限”由创建该对象的系统调用（如open()的mode参数）指定，Linux约定：普通文件的请求权限基准为666（不含x，避免新建文件默认可执行这一安全隐患），目录的请求权限基准为777。因此，umask=022环境下：

  • 新建文件：666 & ~022 = 666 & 755 = 644
  • 新建目录：777 & ~022 = 777 & 755 = 755

umask是进程属性，通过fork()继承，其全局默认值由/etc/login.defs的UMASK参数或PAM的pam_umask模块设定，用户级覆盖通常写入~/.bashrc。安全加固场景中，将默认umask从022收紧至027（去除other的读权限）是CIS Benchmark等基线标准的常见建议项。

1.2.5 特殊权限位：SUID、SGID、Sticky Bit

    特殊权限位占据st_mode的第10-12位（八进制表示中的第一位数字），三者语义独立但均涉及对1.2.1所述标准判定流程的例外覆盖：

（一）SUID（Set User ID，数值4，符号s/S，仅对可执行文件有意义）

    当具有SUID位的可执行文件被execve()调用时，内核将新进程的EUID设置为该文件的属主UID，而RUID保持为调用者的原始UID不变——这正是1.1.1所述凭证四元结构（RUID/EUID分离）在实践中最重要的应用场景。经典范例/usr/bin/passwd：该文件属主为root且设有SUID位，使得任意普通用户执行passwd时能够以root身份写入/etc/shadow（普通用户本身对该文件无写权限），同时进程的RUID仍是调用者本人，passwd程序内部逻辑据此判断”用户只能修改自己的密码，不能修改他人”。

    安全含义：SUID root可执行文件是提权攻击的核心攻击面。 若某SUID二进制程序存在缓冲区溢出、命令注入、或允许通过参数/环境变量控制其行为跳转到/bin/sh（如某些老旧版本的find、vim、nmap在特定编译选项下），攻击者可利用其SUID权限直接获得root shell。这正是1.1.8节所述”项目一”中”SUID文件扫描”功能点的完整理论依据——脚本需要遍历文件系统，识别所有设有SUID位且属主为root的可执行文件，并与已知安全基线（发行版默认SUID文件清单，如GTFOBins收录的高危二进制列表）进行差异比对。

（二）SGID（Set Group ID，数值2，符号s/S）

    对可执行文件：语义与SUID对称，execve()后新进程EGID设置为文件的属组GID。

    对目录（这是运维与安全场景中更常用的形态）：任何在该目录内新建的文件/子目录，其属组自动继承为该目录的属组，而非创建者的主组——此机制常用于团队协作目录（如/srv/shared），确保多用户在共享目录内创建的文件统一归属同一工作组，避免因每个成员主组不同导致的权限碎片化。

（三）Sticky Bit（数值1，符号t/T，主要用于目录）

    设置该位的目录中，即使某用户对目录本身具有w权限（理论上可删除目录内任意条目，参见1.2.2），也只能删除/重命名自己拥有的文件，不能删除其他用户的文件。典型应用是/tmp目录（权限通常为1777），该机制防止了多用户共享临时目录场景下的任意文件删除攻击。

    特殊位的符号表示大小写含义： 大写（S/T）表示该特殊位被设置，但对应的基础执行位（属主/属组/其他的x）未被设置——这通常是一种配置错误信号（例如chmod 4644产生的-rwSr--r--），因为SUID若不伴随x位，在多数系统语义上不产生提权效果，属于无意义甚至具有误导性的权限组合，安全巡检中应对此类”S/T但无x”的异常组合单独标记。

1.2.6 访问控制列表（ACL）：超越rwx三元模型的扩展机制

    标准rwx模型仅支持”属主-属组-其他”三层粒度，无法表达”允许特定的多个用户/组分别拥有不同权限”这类需求，此局限由POSIX ACL弥补：
getfacl /path/to/file # 查看ACL
setfacl -m u:alice:rwx /path/to/file # 为特定用户追加ACL条目
setfacl -m g:devops:r-x /path/to/file # 为特定组追加ACL条目

    设有扩展ACL的文件，ls -l权限字符串末尾会出现+标记（如-rw-r--r--+），这是巡检脚本判断”该文件是否存在超出标准rwx模型的额外授权”的直接信号，若不检查此标记，仅解析标准9位权限位将导致对该文件实际访问范围的误判。

# 验证特殊权限位的数字与符号表示对应关系

ls -l /tmp/test_suid          # 若无属主x位对应，观察 sticky bit 在无x时的大写'T'表现（对目录测试更具代表性，此处用目录验证）

chmod 1777 /tmp/test_sticky
ls -ld /tmp/test_sticky        # 观察权限字符串末位为't'

# 全盘扫描当前系统真实存在的SUID/SGID文件，与1.1.8项目一功能对应
find / -perm -4000 -type f 2>/dev/null    # 查找所有SUID文件
find / -perm -2000 -type f 2>/dev/null    # 查找所有SGID文件

# 验证ACL扩展标记
touch /tmp/test_acl
setfacl -m u:nobody:rwx /tmp/test_acl
ls -l /tmp/test_acl            # 观察权限字符串末尾的'+'标记
getfacl /tmp/test_acl

验证要点：对比find / -perm -4000的实际输出与系统标准SUID文件基线（/usr/bin/passwd、/usr/bin/sudo、/usr/bin/su等应在列表中），任何非标准路径（尤其是/tmp、/var/tmp、用户家目录下）出现的SUID文件，都应作为高优先级异常记录——这一判断逻辑将在1.8节直接转化为Python实现。

1.3 关键账户文件（/etc/passwd、/etc/shadow、/etc/group）

1.3.1 /etc/passwd：完整字段规范

    该文件权限通常为644（全局可读），这一设计决策本身即包含安全前提——密码哈希绝不应存放于此文件，因为任何本地用户都能读取，这正是1.1.1提及的”影子密码机制”存在的根本动因。完整7字段结构：
username:password:UID:GID:GECOS:home_directory:shell

    GECOS字段的内部结构常被忽略：该字段本身可包含以逗号分隔的子字段，历史上遵循全名,房间号,工作电话,住宅电话的约定（源自贝尔实验室GECOS系统的兼容性遗留），现代系统中后三个子字段基本弃用，但finger等工具仍会解析该结构。安全审计角度，GECOS字段一般不具备直接的风险判定价值，但异常巡检脚本若需要生成人类可读报告，可提取该字段首个逗号前的内容作为显示名称。

password字段的取值语义（这是判断账户认证状态的第一入口）：

取值 含义
x 真实密码哈希存放于/etc/shadow（标准影子密码配置）
直接的密码哈希字符串 系统未启用影子密码机制，属严重配置缺陷，任意本地用户可读取全部密码哈希并离线爆破
空字符串 该账户在传统UNIX密码模型下允许空密码登录（是否真正生效仍取决于PAM配置及/etc/shadow中对应字段，需结合1.3.3判断）

1.3.2 /etc/shadow：完整字段规范与访问控制

该文件权限严格限制为640或600，属主为root，属组通常为shadow（部分发行版设计为允许该组内服务读取，如密码策略校验服务），这一权限设置本身就是1.2节权限模型在关键系统文件上的具体应用范例。9字段结构：
username:password_hash:lastchg:min:max:warn:inactive:expire:reserved

字段位 名称 语义
1 用户名 与/etc/passwd第1字段关联的外键
2 密码哈希 详见1.3.3
3 最后修改日期 自Unix纪元（1970-01-01）起的天数，非秒数
4 最小修改间隔 密码修改后，再次允许修改前必须经过的最小天数（防止用户通过连续修改绕过历史密码检查）
5 最大有效期 超过该天数未修改密码则强制过期，99999通常表示实质上永不过期
6 到期警告期 密码到期前多少天开始向用户发出警告
7 宽限失效期 密码过期后，账户仍可被视为”未完全禁用”的天数，超过后账户被系统标记为inactive
8 账户绝对过期日期 自Unix纪元起的天数，达到该日期后账户整体失效（区别于密码过期，这是账户级别的硬性失效点，常用于临时账户管控）
9 保留字段 未使用

字段3-8共同构成密码时效策略（Password Aging Policy），是CIS Benchmark等安全基线审计的核心对象。 安全巡检中，字段5（最大有效期）为空或为极大值（如99999）且字段8（账户过期日期）为空，意味着该账户的密码策略实质上是”永不过期”，对于特权账户而言这是需要标记的高优先级风险项。

1.3.3 密码哈希格式解析

/etc/shadow第2字段遵循模块化加密格式（Modular Crypt Format）：
$id$salt$hash

id标识符 对应算法 安全评价
1 MD5 已被密码学界判定为不安全，现代系统不应再产生此类哈希
2a/2y Blowfish (bcrypt) 部分系统使用，具备可调计算成本因子
5 SHA-256 现代Linux发行版常见默认
6 SHA-512 当前主流默认算法，$6$前缀，计算成本高于$5$，是多数现代发行版useradd/passwd的默认选择
y/gy yescrypt 近年新发行版（如新版Debian/Fedora）逐步转向的内存困难型算法，专门针对GPU并行破解进行了抗性设计

非哈希特殊取值（用于账户状态标记，而非表示”某种密码”）：

  • !或!!：账户密码被锁定（通常由passwd -l或usermod -L产生），原密码哈希仍保留在!之后（可通过对比锁定前后差异复原），该账户无法通过密码方式认证，但若配置了SSH密钥认证，该锁定不影响密钥登录——这是一个高频被误解的安全盲点：运维人员误以为”锁定密码=禁用账户”，但SSH公钥认证路径完全绕过/etc/shadow密码字段的检查。
  • *：账户被明确禁用，且不保留可复原的原始哈希，通常用于系统服务账户（如daemon、bin），表示该账户从设计上就不允许密码认证。
  • 空字符串：允许空密码登录（是否真正可利用仍取决于PAM是否配置了nullok选项，二者构成AND关系，需联合读取/etc/pam.d/system-auth或/etc/pam.d/sshd进行完整判断）。

1.3.4 /etc/group与/etc/gshadow

/etc/group结构已在1.1.2节说明。/etc/gshadow是/etc/group的影子对应文件，权限同样受限（640或000），结构：
group_name:password_hash:administrators:members

administrators字段记录该组的管理员用户（拥有通过gpasswd管理该组成员的权限，无需root），password_hash字段对应newgrp切换组时可能要求输入的组密码——此机制在现代系统中已基本弃用（组管理普遍改用sudo+usermod模式），巡检中若发现/etc/gshadow中存在非空且非锁定标记的组密码哈希，属于遗留配置，应作为低优先级但值得记录的加固建议项。

1.3.5 三文件的关联完整性校验

三个文件之间通过用户名/组名形成隐式外键关系，但系统本身不强制这种引用完整性，因此会产生若干类需要巡检脚本主动检测的不一致状态：

  1. /etc/passwd中存在的用户名，在/etc/shadow中无对应行——该账户实质上无法通过密码认证（部分系统会将其视为异常，因为标准工具链在创建用户时应同步产生两侧记录）。
  2. /etc/passwd第4字段（主组GID）在/etc/group中不存在对应GID——即所谓”悬空主组”，ls -l此类用户拥有的文件时属组会直接显示数字GID而非组名，是配置腐化的直接信号。
  3. /etc/shadow存在但/etc/passwd中无对应用户名——理论上不应出现，但在账户删除操作使用了非标准工具（直接编辑文件而非userdel）时可能产生此类残留，属于清理不彻底的痕迹，也可能是隐藏账户的手法之一（部分权限提升脚本会尝试仅操作影子文件而遗漏passwd同步，但更常见的隐藏手法恰恰相反：仅在passwd中留痕）。

pwck与grpck是系统自带的一致性校验工具，分别针对上述passwd/shadow与group/gshadow的关联完整性进行检查，其检测逻辑与巡检脚本需要覆盖的检查项高度重合，可作为1.8节脚本设计时的参照基准，而非重复造轮子——生产环境中更常见的做法是脚本内部封装调用pwck -r（只读模式）并解析其输出，而非重新实现全部校验逻辑。

1.3.6 实验验证方案

# 查看当前系统的密码哈希算法分布
sudo awk -F: '{print $2}' /etc/shadow | grep -oP '^\$\K[^$]+' | sort | uniq -c

# 定位所有密码字段为空的账户（潜在空密码登录风险）
sudo awk -F: '($2==""){print $1}' /etc/shadow

# 定位所有密码被锁定的账户
sudo awk -F: '($2 ~ /^!/){print $1}' /etc/shadow

# 定位密码永不过期的账户（第5字段为空或99999）
sudo awk -F: '($5=="" || $5==99999){print $1}' /etc/shadow

# 一致性校验：查找悬空主组（passwd中GID在group中不存在）
awk -F: '{print $4}' /etc/passwd | sort -u > /tmp/passwd_gids.txt
awk -F: '{print $3}' /etc/group | sort -u > /tmp/group_gids.txt
comm -23 /tmp/passwd_gids.txt /tmp/group_gids.txt

# 使用系统自带工具做完整一致性校验
sudo pwck -r
sudo grpck -r

验证要点：将第一条命令的输出与你系统的发行版及创建时间对照，确认默认哈希算法是否符合预期（近年安装的系统应以$6$或y为主）；若存在历史遗留的$1$（MD5）哈希账户，应作为高优先级加固项记录——这类账户很可能是系统迁移或长期未强制轮换密码策略的产物。

1.4 SSH服务配置与加固

1.4.1 协议架构与认证通路的独立性

    SSH（Secure Shell）建立连接分为两个逻辑独立的阶段：传输层协议（Transport Layer Protocol，负责服务端身份验证、密钥交换与加密信道建立）与用户认证协议（User Authentication Protocol，负责验证客户端身份）。这一分层是理解1.3.3节所述”密码锁定不影响密钥认证”现象的协议层根源——传输层建立完成后，认证协议可依次尝试多种独立的认证方法（publickey、password、keyboard-interactive等），每种方法各自决定是否放行，/etc/shadow的密码字段仅被password方法查询，与publickey方法完全无关联，二者在协议设计上就是两条不共享判定逻辑的独立路径。

    服务端配置文件为/etc/ssh/sshd_config，客户端全局配置为/etc/ssh/ssh_config，用户级客户端配置为~/.ssh/config。所有对sshd_config的修改需执行sshd -t进行语法校验后重启服务生效，语法错误可能导致服务无法启动，是生产环境变更需要严格测试的原因。

1.4.2 公钥认证机制与非对称密码学基础

    公钥认证基于非对称加密的挑战-响应模型：客户端持有私钥（~/.ssh/id_ed25519或id_rsa等，权限必须为600，否则ssh客户端将拒绝使用该私钥），服务端在~/.ssh/authorized_keys（属主家目录，权限须为700目录+600文件，宽松权限会被sshd直接拒绝识别该文件）中存放对应公钥。认证过程中私钥从不通过网络传输，服务端生成随机挑战，客户端用私钥签名后返回，服务端用已知公钥验签，全程私钥不出本地。

密钥算法选择的安全考量：

算法 特性
RSA 传统兼容性最佳，建议密钥长度不低于3072位（2048位已被NIST建议逐步淘汰）
ECDSA 基于椭圆曲线，性能优于RSA，但曲线参数选择存在历史争议（部分曲线的生成过程缺乏透明度）
Ed25519 现代推荐首选，固定256位安全强度，抗侧信道攻击设计更完善，密钥与签名尺寸小，是当前新部署环境的事实标准

authorized_keys每行可附加选项前缀，是精细化访问控制的关键机制，常被忽略：
command=”/usr/local/bin/backup-only.sh”,no-port-forwarding,no-X11-forwarding,from=”10.0.0.0/24” ssh-ed25519 AAAA… comment

  • command=：强制该密钥登录后只能执行指定命令，忽略客户端请求的实际命令，是构建”仅允许执行特定操作的受限账户”（如自动化备份账户）的标准做法。
  • from=：限制该密钥仅能从指定IP/网段发起连接，即使私钥泄露，攻击者也需同时具备源IP伪装或网络位置才能利用。
  • no-port-forwarding/no-agent-forwarding/no-X11-forwarding：禁用该密钥关联会话的端口转发、代理转发、X11转发能力，缩小该密钥被滥用为跳板的攻击面。

安全巡检中，authorized_keys文件权限异常（如被设置为组或其他用户可写）本身就构成严重漏洞——攻击者若能写入该文件即可无需任何密码直接植入后门公钥，此为SSH持久化攻击中最常见的手法之一，检测逻辑应覆盖文件权限位与属主的双重校验。

1.4.3 sshd_config核心加固参数

指令 加固建议值 安全依据
PermitRootLogin no（或至少prohibit-password） 阻止root直接通过SSH登录，强制先以普通用户登录再sudo提权，确保操作留有可追溯的身份切换审计痕迹
PasswordAuthentication no 完全禁用密码认证，仅保留公钥认证，从根本上消除密码爆破攻击面
PermitEmptyPasswords no 防止1.3.3节所述空密码账户通过SSH被直接利用
MaxAuthTries 3-4 限制单次连接的认证尝试次数，提高自动化爆破的时间成本
LoginGraceTime 30（秒） 限制未完成认证的连接占用时长，缓解连接耗尽型拒绝服务
ClientAliveInterval / ClientAliveCountMax 300 / 2 控制空闲会话的存活探测与超时断开策略，减少悬挂会话被劫持的风险窗口
X11Forwarding no（非必要场景） 减少图形转发相关的额外攻击面
AllowUsers / AllowGroups 按需显式列出 白名单机制，从sshd层面直接限定允许登录的账户范围，即使账户存在也无法通过SSH认证，构成纵深防御的第二层账户级控制
Protocol 2（现代sshd已不再支持协议1，此项通常无需显式设置） SSH协议1存在已知密码学缺陷，早期版本需显式禁用
LogLevel VERBOSE或以上 提高审计日志粒度，VERBOSE级别会记录密钥指纹，便于事后追溯具体使用了哪一把密钥完成认证

1.4.4 主机密钥与中间人攻击防护

服务端持有的主机密钥（Host Key，位于/etc/ssh/ssh_host_*_key）用于客户端在传输层验证”当前连接的服务端确实是预期主机”，其公钥指纹存储于客户端的~/.ssh/known_hosts。首次连接陌生主机时的指纹确认提示（Are you sure you want to continue connecting?）正是这一机制的用户可见部分——若指纹与known_hosts中已记录的不一致，ssh客户端会发出强烈警告并默认拒绝连接，这是检测中间人攻击（攻击者伪装目标主机拦截凭证）的核心防线，生产环境中不应养成”看到警告直接删除known_hosts条目重新连接”的操作习惯，而应先核实主机密钥是否因合法的系统重装/密钥轮换而变化。

1.4.5 面向安全审计的SSH配置巡检要点

结合上述机制，主机侧SSH安全巡检应至少覆盖：

  1. sshd_config高危配置项扫描：解析实际生效配置（sshd -T输出合并后的最终生效值，优于直接读取配置文件，因为存在Include指令引入的分片配置及命令行参数覆盖的可能）。
  2. authorized_keys文件权限与内容审计：遍历所有用户家目录，检查该文件及其所在.ssh目录的权限是否符合700/600标准，并记录其中是否存在附带command=等限制选项的密钥（这类密钥通常是自动化账户的合法配置，不应与普通交互密钥混淆判断）。
  3. 主机密钥算法与强度：确认/etc/ssh/sshd_config中HostKey指令引用的密钥类型不包含已弃用的DSA。
  4. 登录来源与时间异常关联：结合1.5节journalctl对sshd服务日志的解析，识别非工作时间/非常规地理位置的成功登录事件，此项需要与1.6节网络诊断及日志时间戳分析联合完成。

1.4.6 实验验证方案

# 生成Ed25519密钥对（现代推荐算法）
ssh-keygen -t ed25519 -C "audit-test"

# 查看当前sshd合并后的最终生效配置（而非仅读取配置文件原文）
sudo sshd -T | grep -E "^(permitrootlogin|passwordauthentication|permitemptypasswords|maxauthtries|x11forwarding)"

# 校验authorized_keys及其父目录权限是否符合标准

# 语法校验配置文件（修改sshd_config后，重启服务前必须执行此步）

1.5 进程与服务管理（systemd、journalctl）

1.5.1 进程模型基础：/proc虚拟文件系统

Linux将进程运行时状态以虚拟文件系统的形式暴露于/proc/<PID>/目录下，ps、top等工具本质上都是对该目录结构的解析封装，而非通过特殊系统调用直接获取内核数据结构。理解这一点对于1.7节使用psutil编写巡检脚本至关重要——psutil库在Linux平台的底层实现同样是读取/proc下的对应文件，其性能特征与限制（如对/proc/<PID>/的读取存在竞态条件，进程可能在两次读取之间已退出）直接继承自这一机制。

关键子文件及其安全审计价值：

路径 内容 审计价值
/proc/<PID>/cmdline 完整命令行参数（\0分隔） 识别进程的真实启动方式，注意该字段可被进程自身通过修改argv指针内容而伪造（常见于试图隐藏真实命令行的恶意进程，即”进程名伪装”技术），不能作为唯一可信来源
/proc/<PID>/exe 指向实际可执行文件的符号链接 若该链接目标路径包含(deleted)后缀，表明进程仍在运行但其对应磁盘文件已被删除——这是内存驻留型恶意代码的经典特征之一，因为攻击者常在进程启动后立即删除落地文件以规避基于文件的检测
/proc/<PID>/status 进程状态摘要，含真实/有效UID等凭证信息 直接暴露1.1.1所述RUID/EUID分离状态，可用于检测异常的权限提升进程
/proc/<PID>/fd/ 该进程当前打开的全部文件描述符 识别进程实际持有的网络连接、打开文件，是lsof工具的数据来源，也是排查”进程访问了哪些非预期文件”的直接证据
/proc/<PID>/environ 进程环境变量 部分持久化/提权手法依赖特定环境变量（如LD_PRELOAD），此文件可用于检测异常注入

1.5.2 进程状态机与僵尸/孤儿进程

内核为每个进程维护状态字段，ps输出中的STAT列即反映该状态（R运行/可运行、S可中断睡眠、D不可中断睡眠、T已停止、Z僵尸）：

  • 僵尸进程（Zombie, Z）：进程已终止但其父进程尚未调用wait()/waitpid()回收其退出状态，内核保留其PID及退出码等最小信息在进程表中。僵尸进程不占用内存或CPU资源，但会占用有限的PID命名空间，大量僵尸进程堆积通常指示父进程存在编程缺陷（未正确处理子进程退出信号SIGCHLD），本身不构成直接安全威胁但是代码质量与稳定性的指示器。
  • 孤儿进程（Orphan）：父进程先于子进程终止，该子进程被内核**重新收养（reparent）**给init（PID 1，现代系统即systemd）或距其最近的“子进程收割者”（subreaper，通过prctl(PR_SET_CHILD_SUBREAPER)设置，容器运行时常用此机制接管容器内的孤儿进程）。安全审计中，若发现某进程的父PID为1，但该进程的启动时间与systemd管理的服务单元生命周期不吻合，需要考察其原始父进程是否已被恶意终止以掩盖调用链——这是进程树分析中识别”伪装成正常孤儿进程的恶意驻留进程”的关键切入点。

1.5.3 systemd架构：PID 1与单元（Unit）模型

systemd作为现代Linux发行版的初始化系统与服务管理框架，以PID 1运行，是所有其他进程（含孤儿进程收养链）的最终祖先。其管理对象抽象为单元（Unit），常见类型：

单元类型 后缀 用途
service .service 定义一个后台服务的启动、停止、重启行为
socket .socket 实现基于套接字的按需启动（socket activation），如sshd.socket可在首个连接到达时才拉起sshd.service
target .target 逻辑分组，用于表达单元间的依赖与启动顺序，类似传统SysV的运行级别（runlevel）但更灵活
timer .timer systemd原生的定时任务机制，功能上替代cron的部分场景，具备更精细的依赖控制与日志集成
mount / automount .mount/.automount 文件系统挂载点的声明式管理

单元文件搜索路径与优先级（从低到高覆盖）：

  1. /usr/lib/systemd/system/：发行版软件包安装的默认单元文件
  2. /etc/systemd/system/：系统管理员的本地覆盖，优先级高于上者，是手工加固/自定义配置的标准落地位置
  3. /etc/systemd/system/<unit>.d/*.conf：drop-in覆盖片段，无需完整重写整个单元文件即可覆盖/追加特定指令，是官方推荐的配置定制方式（避免直接修改包管理器维护的文件导致后续升级冲突）

安全审计中，/etc/systemd/system/下出现的、并非通过正规软件包安装产生的服务单元文件，是持久化攻击的常见形式之一——攻击者可创建一个伪装成系统服务的单元文件（如命名为systemd-network-helper.service），配置WantedBy=multi-user.target使其开机自启，以此绕过传统基于crontab或~/.bashrc的持久化检测思路。

1.5.4 服务单元文件结构与安全加固指令

一个典型.service单元文件包含三个节（section）：
[Unit]
Description=Example Hardened Service
After=network.target

[Service]
ExecStart=/usr/local/bin/myservice
User=svc_myservice
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
Restart=on-failure

[Install]
WantedBy=multi-user.target

关键加固指令的安全语义：

指令 作用
User=/Group= 以非root专用账户运行服务，遵循最小权限原则，避免服务漏洞直接导致root级别的入侵影响
NoNewPrivileges=true 阻止该进程及其子进程通过execve()获取比父进程更高的权限（包括阻断SUID二进制的提权效果），是内核prctl(PR_SET_NO_NEW_PRIVS)机制的声明式封装
ProtectSystem=strict/full/true 将/usr、/boot等系统目录挂载为只读（strict级别扩展至几乎整个文件系统），限制被入侵服务篡改系统文件的能力
PrivateTmp=true 为该服务分配独立的/tmp、/var/tmp命名空间视图，防止与其他进程共享临时目录导致的符号链接攻击或信息泄露
CapabilityBoundingSet= 显式声明该服务允许保留的Linux Capabilities子集，未列出的能力即使以root身份启动也无法使用，是1.2.1节CAP_DAC_OVERRIDE等能力概念在实践中的精细化收紧应用

systemd-analyze security <unit>命令可自动评估某服务单元的加固指令覆盖情况并给出量化风险评分，是快速审计现有服务安全配置完整性的实用工具。

1.5.5 systemctl常用操作与状态语义

systemctl status sshd          # 查看运行状态、最近日志摘要、控制组(cgroup)内进程树
systemctl start/stop/restart sshd
systemctl enable/disable sshd  # 控制是否随开机自启（创建/删除symlink到WantedBy指定的target）
systemctl mask sshd            # 将单元文件链接到/dev/null，即使显式start也无法启动，比disable更强的禁用手段
systemctl list-units --type=service --state=running
systemctl list-unit-files --state=enabled   # 审计所有开机自启的单元，是持久化排查的常规起点

enable与mask的差异需要精确区分：disable仅移除自启动触发条件，仍可被手动或依赖关系间接启动；mask从根本上阻断该单元被任何方式启动，是应对”已确认恶意但暂不删除以保留取证证据”场景的标准处置手段。

1.5.6 journalctl：结构化日志的查询与关联分析

systemd-journald以二进制格式（而非传统纯文本）集中存储日志，支持字段索引查询，存储位置分为：

  • /run/log/journal/：易失性存储，仅内存/tmpfs，重启后丢失
  • /var/log/journal/：持久化存储，需该目录存在（部分发行版默认不启用持久化，需手动创建该目录并重启journald生效）

核心查询参数：
journalctl -u sshd.service # 按单元过滤
journalctl -u sshd.service -f # 实时跟踪（类似tail -f）
journalctl –since “2026-09-17 08:00” –until “2026-09-17 12:00” # 时间范围过滤
journalctl -p err # 按优先级过滤（emerg/alert/crit/err/warning/notice/info/debug）
journalctl _UID=1000 # 按发起进程的UID过滤，直接对应1.1.1所述凭证模型
journalctl –disk-usage # 查看日志占用磁盘空间
journalctl -o json-pretty # 结构化JSON输出，便于1.7节Python脚本直接解析而非正则匹配纯文本

journalctl -o json-pretty这一形式对巡检脚本编写具有实质意义：相较于解析传统/var/log/auth.log等纯文本格式（格式因发行版、rsyslog配置差异而不统一），journald的JSON输出提供结构化字段（如_PID、_UID、_COMM、MESSAGE），显著降低正则表达式解析的脆弱性，是1.7节实现”异常登录检测”功能时应优先考虑的数据源，而非依赖传统文本日志格式假设。

1.5.7 面向安全审计的进程与服务巡检要点

  1. 开机自启服务清单基线比对：systemctl list-unit-files --state=enabled的输出应与系统初始基线快照比对，任何新增的自启动服务都需要溯源其来源（软件包安装产生 vs 手工/脚本创建）。
  2. 非标准路径的单元文件扫描：重点检查/etc/systemd/system/下不属于已安装软件包管理记录（可用rpm -qf/dpkg -S反查文件归属）的单元文件。
  3. /proc/<PID>/exe指向(deleted)的运行中进程：结合1.5.1所述机制，作为高优先级异常直接标记。
  4. 高资源占用进程Top N：对应项目一”异常进程检查”功能点，需要结合CPU/内存占用与该进程的启动时间、父进程、可执行文件路径的合理性联合判断，而非仅按资源占用排序即得出结论。
  5. journalctl中sshd/sudo/su相关事件的时间序列分析：识别短时间内大量认证失败（暴力破解特征）或非常规时间段的成功认证事件。

1.6 网络诊断命令（ss、lsof、netstat）

1.6.1 套接字的文件描述符抽象与内核关联机制

Linux将网络套接字纳入统一的”一切皆文件”抽象，每个套接字在内核中对应一个唯一的inode编号，该inode通过进程的文件描述符表与具体进程关联。这一机制是1.5.1节/proc/<PID>/fd/目录的直接延伸：该目录下若存在指向socket:[12345]形式的符号链接，即表示该进程持有一个inode为12345的网络套接字。

内核同时在/proc/net/tcp、/proc/net/tcp6、/proc/net/udp等文件中，以文本表格形式暴露系统全部套接字的状态信息（本地/远端地址端口、连接状态、关联的inode）。ss、lsof、netstat等工具的核心工作原理，正是将/proc/net/*中记录的inode与遍历所有进程/proc/<PID>/fd/得到的inode进行关联匹配，从而实现”哪个进程持有哪个网络连接”这一映射关系的构建。理解这一底层匹配机制，是判断”为什么某些工具需要root权限才能看到进程归属”（普通用户无权遍历他人进程的/proc/<PID>/fd/）以及”为什么该映射在高并发场景下可能出现短暂不一致”（两次读取之间状态已变化，属于固有的竞态窗口）的关键。

1.6.2 TCP状态机与安全含义

TCP连接生命周期由内核维护的有限状态机描述，巡检与排查中需要重点关注的状态：

状态 含义 安全/运维关注点
LISTEN 被动打开，等待入站连接 对应”监听端口”，是攻击面枚举的第一层数据——每一个LISTEN状态的端口都是潜在的入站攻击入口
ESTABLISHED 连接已建立，可双向传输数据 巡检中需要区分该连接是本机作为服务端被连入，还是本机主动作为客户端向外连出（后者若目标为非常规地址，是反弹连接/命令控制信道的典型特征）
TIME_WAIT 主动关闭方在连接结束后的强制等待状态，用于确保迟到的报文段被正确丢弃 大量堆积通常是短连接高并发服务的正常现象，而非安全问题，但异常暴涨可能指示端口扫描等行为留下的痕迹
CLOSE_WAIT 被动关闭方已收到对端FIN，但本地应用尚未调用close() 长时间大量堆积通常指示应用层存在未正确关闭连接的编程缺陷（资源泄漏），而非直接的安全威胁
SYN_RECV 收到SYN但三次握手尚未完成 短时间大量此状态的连接是SYN Flood拒绝服务攻击的直接特征

1.6.3 ss：现代套接字查询工具

ss（socket statistics）基于内核netlink接口直接查询套接字信息，相较于netstat解析/proc/net/*文本文件的方式，在套接字数量庞大的场景下具备显著性能优势，这是ss成为现代发行版首选工具、net-tools软件包（含netstat）在多数发行版中已不再默认安装的核心原因。

核心参数：
ss -tulpn

参数 语义
-t 显示TCP套接字
-u 显示UDP套接字
-l 仅显示处于LISTEN状态的套接字
-p 显示套接字关联的进程（PID/进程名），需要root权限或该套接字属于当前用户
-n 以数字形式显示地址与端口，不进行DNS反向解析（避免因DNS查询延迟拖慢命令响应，也避免巡检脚本因DNS解析结果被污染而产生误判）

其他关键用法：
ss -tan state established # 按状态过滤，仅查看已建立的TCP连接
ss -s # 汇总统计（各状态套接字数量），可用于快速判断是否存在SYN Flood等异常
ss -o state established ‘( dport = :443 )’ # 支持表达式过滤特定端口/状态组合

1.6.4 lsof：更广义的文件描述符视角

lsof（List Open Files）覆盖范围超越网络套接字，涵盖进程打开的全部文件描述符类型（普通文件、目录、管道、字符设备、网络套接字等），网络相关查询通过-i参数聚焦：
lsof -i :22 # 查看占用22端口的进程
lsof -i TCP -sTCP:LISTEN # 仅列出处于LISTEN状态的TCP套接字
lsof -p # 查看指定进程打开的全部文件描述符（含日志文件、配置文件、动态库等）
lsof -i -P -n # -P禁止端口号被服务名替代（如80显示为http），-n禁止地址反向解析，语义与ss的-n参数动机一致

lsof -p <PID>在安全事件响应中的价值超出网络排查范畴——通过查看某可疑进程完整的打开文件列表，可以推断其正在读写的数据文件、加载的动态链接库（若存在指向非标准路径的.so文件，可能指示动态库劫持攻击）、以及是否持有远超预期数量的文件描述符（资源耗尽型异常或数据渗出行为的迹象）。

1.6.5 netstat：遗留工具与迁移对照

尽管ss已成为主流，理解netstat仍有必要——部分老旧系统、精简容器镜像默认仅安装net-tools，且大量历史文档与运维脚本仍基于netstat语法：

netstat命令 ss等价命令
netstat -tulpn ss -tulpn
netstat -an | grep ESTABLISHED ss -tan state established
netstat -r ip route（现代系统路由表查询已迁移至iproute2工具集）

1.6.6 进程-连接映射在安全巡检中的完整应用

综合1.6.1-1.6.4，构建”监听端口提取”这一巡检功能的完整数据链路为：

  1. 通过ss -tulpn（或psutil.net_connections()，见1.7节）获取全部监听套接字，含本地端口、协议、关联PID。
  2. 对每个PID，交叉查询/proc/<PID>/exe获取实际可执行文件路径，/proc/<PID>/cmdline获取启动命令（注意1.5.1节所述该字段可被伪造的局限性）。
  3. 将（端口, 可执行文件路径, 属主UID）三元组与预先建立的基线（首次巡检记录的”正常”监听服务清单）比对，任何新增的监听端口、或已知端口关联的可执行文件路径发生变化（如80端口不再由标准nginx路径的进程持有，而是变为/tmp/.hidden/x），均应标记为高优先级异常。
  4. 对ESTABLISHED状态的出站连接，重点关注目标地址是否为非常规的公网IP、目标端口是否为非标准的高位端口（常见于反弹shell与命令控制信道，尽管现代恶意软件也大量使用443等标准端口伪装以规避此类简单端口特征检测，因此端口特征仅作为辅助信号，不能作为唯一判据）。

这一完整链路正是项目一”监听端口提取”功能模块在1.8节的实现蓝图，ss/lsof的命令行输出或psutil的等价API调用二选一均可，但底层数据源与关联逻辑一致。

1.6.7 实验验证方案

# 查看当前所有监听端口及其归属进程
sudo ss -tulpn

# 验证进程-套接字的inode关联机制：手动追踪一个具体连接
# 第一步：找到sshd监听套接字的inode
sudo ss -tlpn | grep :22

# 第二步：在/proc/net/tcp中定位对应记录（注意端口号以十六进制显示，22对应0016）
sudo cat /proc/net/tcp | grep ":0016"

# 第三步：验证sshd进程的fd目录中存在指向该inode的socket链接
sudo ls -l /proc/$(pgrep -o sshd)/fd/ | grep socket

# 对比ss与lsof在同一端口上的输出一致性
sudo lsof -i :22

# 观察TCP状态机分布，识别是否存在异常堆积
ss -s

# 建立"当前监听端口基线"快照，作为后续巡检脚本比对的参照
sudo ss -tulpn | awk 'NR>1{print $1,$5}' | sort -u > /tmp/listening_baseline.txt
cat /tmp/listening_baseline.txt

验证要点：第二、三步是本节最关键的实证环节——手动完成一次”端口→inode→fd→进程”的完整追踪链路，能够真正理解ss -p背后自动化完成的匹配过程，而非把该工具当作黑盒使用。这一理解直接决定你在1.8节用psutil实现同等功能时，能否正确处理该库在特定权限/命名空间隔离场景下可能出现的映射失败情况。

1.7 Python系统编程基础（subprocess、psutil、csv、正则）

1.7.1 subprocess：进程调用的安全边界

subprocess模块用于在Python进程中派生子进程并与之交互，是1.6节命令行工具（ss、find、pwck等）与Python脚本之间的桥梁。现代API的推荐入口是subprocess.run()：
import subprocess

result = subprocess.run(
    ["ss", "-tulpn"],
    capture_output=True,
    text=True,
    timeout=5,
    check=False
)
参数 语义
第一个位置参数 列表形式的命令与参数，而非拼接字符串——这是1.7.2节将展开的注入防护核心
capture_output=True 等价于同时设置stdout=subprocess.PIPE, stderr=subprocess.PIPE，捕获输出到result.stdout/result.stderr
text=True 以字符串（而非字节串bytes）形式返回输出，内部按系统默认编码解码
timeout 超时后抛出subprocess.TimeoutExpired，防止巡检脚本因某个子命令挂起（如对无响应挂载点的find遍历）而整体阻塞
check 为True时，若子进程返回非零退出码则抛出subprocess.CalledProcessError；巡检脚本中通常设为False并手动检查result.returncode，因为部分命令（如未找到匹配项的grep）的非零退出码属于正常业务语义而非错误

1.7.2 命令注入风险与shell=True的危险性

# 危险写法：shell=True配合字符串拼接
user_input = "someuser; rm -rf /"
subprocess.run(f"id {user_input}", shell=True)   # 灾难性后果

shell=True使得传入的字符串被交由系统shell（/bin/sh）解释执行，此时shell的元字符（;、|、&、`、$()等）会被正常解析，若命令字符串中拼接了任何外部输入（哪怕仅仅是巡检脚本读取的另一个文件路径），即构成命令注入漏洞的完整攻击面——这与Web安全中的SQL注入是同一类”数据与代码边界混淆”问题在系统编程层面的对应形态。

正确实践： 始终使用列表形式传参且不设置shell=True（该模式下参数直接通过execve()传递给目标程序，不经过shell解释，元字符不具备特殊含义）；确需使用shell特性（管道、通配符展开）时，应对每个外部输入变量使用shlex.quote()进行转义后再拼接，或改用Python原生实现管道逻辑（如多个subprocess.Popen对象通过stdin/stdout直接连接）以完全规避shell层。安全巡检脚本作为直接操作主机、通常以较高权限运行的工具，其自身若存在命令注入缺陷，将构成比它试图检测的问题更严重的安全隐患，这是编写此类工具时必须置于最高优先级的设计约束。

1.7.3 psutil：跨平台系统信息库与/proc的映射关系

psutil在Linux平台的实现本质是对1.5.1、1.6.1节所述/proc/<PID>/*与/proc/net/*的封装，提供面向对象的稳定API，规避直接解析这些文件格式时因内核版本差异导致的脆弱性。
import psutil

for proc in psutil.process_iter(['pid', 'name', 'username', 'cpu_percent', 'memory_percent']):
    try:
        info = proc.info
        print(info['pid'], info['username'], info['name'],
              info['cpu_percent'], info['memory_percent'])
    except (psutil.NoSuchProcess, psutil.AccessDenied, psutil.ZombieProcess):
        continue

必须处理的三类竞态异常，这是1.6.1节所述”两次/proc读取之间状态已变化”这一固有竞态窗口在API层面的具体体现：

异常 触发场景
psutil.NoSuchProcess 遍历过程中该进程已终止，其/proc/<PID>/目录已被内核回收
psutil.AccessDenied 当前用户权限不足以读取目标进程的敏感信息（通常发生在非root权限运行巡检脚本、试图访问其他用户所属进程的场景），这是巡检脚本必须以root权限运行才能获得完整可见性的直接原因
psutil.ZombieProcess 目标为1.5.2节所述僵尸进程，其大部分信息字段已不可获取

网络连接查询（对应1.6节ss功能的Python实现）：
connections = psutil.net_connections(kind=’tcp’)
for conn in connections:
if conn.status == ‘LISTEN’:
pid = conn.pid # 可能为None：表示当前进程权限不足以确定归属，而非该端口无进程持有
laddr = conn.laddr # (ip, port)具名元组

conn.pid为None时的处理逻辑需要格外注意：这并不代表该套接字没有归属进程（内核层面每个套接字必然有归属），而是psutil在权限不足时无法完成1.6.1节所述inode匹配过程，若脚本未以root权限运行，应在报告中明确标注”权限不足，归属未知”，而非默认将其归类为”无主套接字”这一具有误导性的结论。

1.7.4 csv模块：结构化报告输出

巡检脚本的核心交付物是结构化的CSV报告（对应项目一的输出要求），推荐使用csv.DictWriter而非手工拼接逗号分隔字符串——后者在字段本身包含逗号、引号或换行符时会产生格式错误的输出：
import csv

fieldnames = ['检查项', '风险等级', '详情', '建议']
with open('audit_report.csv', 'w', newline='', encoding='utf-8-sig') as f:
    writer = csv.DictWriter(f, fieldnames=fieldnames)
    writer.writeheader()
    writer.writerow({
        '检查项': 'SUID文件扫描',
        '风险等级': '高',
        '详情': '/tmp/.hidden/x 存在非常规路径SUID位',
        '建议': '核实该文件来源并考虑立即移除执行权限'
    })

newline=''是Python官方文档明确要求的写法（避免在Windows平台产生多余空行，跨平台脚本应始终遵循）；encoding='utf-8-sig'（带BOM的UTF-8）可确保Excel等工具正确识别中文字段，避免打开报告时出现乱码——这是国内安全运维场景中容易被忽略但影响实际可用性的细节。

1.7.5 正则表达式：日志解析的适用边界

re模块用于从非结构化文本（如传统/var/log/auth.log）中提取结构化字段，但1.5.6节已指出，journalctl -o json-pretty能提供原生结构化数据，应作为优先数据源，正则解析仅用于处理确实只能以纯文本形式获取的遗留日志。
import re

pattern = re.compile(
    r'Failed password for (invalid user )?(?P<user>\S+) from (?P<ip>\d+\.\d+\.\d+\.\d+) port (?P<port>\d+)'
)
match = pattern.search(log_line)
if match:
    user = match.group('user')
    ip = match.group('ip')

命名捕获组（(?P<name>...)） 相较于位置索引捕获组，显著提升脚本可维护性——正则表达式本身随日志格式变化调整时，位置索引易发生错位导致静默取错字段，命名捕获组在结构调整时能更早暴露不匹配问题。

正则解析日志的固有局限（应在项目一的README中明确说明，这也是面试问答卡中”为什么正则解析可能不可靠”这类追问的标准答案方向）： 日志格式可能随发行版版本、sshd版本、syslog/rsyslog/syslog-ng配置差异而变化，正则表达式对格式变化零容错，一旦不匹配将静默丢失该条记录而非报错——这是正则方案相较于结构化日志查询（1.7.3节journalctl -o json-pretty路径）在健壮性上的根本劣势，也是巡检脚本应当优先选择结构化数据源、仅在别无选择时才退化为正则解析的核心理由。

1.7.6 错误处理的整体设计原则

巡检脚本作为诊断工具，其自身的健壮性要求与普通业务脚本不同：单个检查项的失败不应导致整个巡检流程中断。因此每个功能模块应独立捕获异常并在报告中记录”该项检查失败及原因”，而非让脚本在遍历到某个异常进程时直接崩溃退出：
def check_suid_files():
try:
result = subprocess.run(
[“find”, “/“, “-perm”, “-4000”, “-type”, “f”],
capture_output=True, text=True, timeout=60
)
return result.stdout.strip().split(‘\n’) if result.stdout else []
except subprocess.TimeoutExpired:
return [“[检查超时，可能存在异常慢速文件系统挂载点]”]
except Exception as e:
return [f”[检查失败: {e}]”]

这一”隔离失败、继续执行、如实记录”的设计原则，将在1.8节四个功能模块的整体架构中统一应用。

1.7.7 实验验证方案

# 综合验证脚本：整合前六节的检测点，作为1.8节项目一的雏形
import psutil
import subprocess
import csv

# 验证点一：遍历进程并处理竞态异常（对应1.5.2节进程状态与1.7.3节异常处理）
for proc in psutil.process_iter(['pid', 'name', 'username']):
    try:
        print(proc.info)
    except (psutil.NoSuchProcess, psutil.AccessDenied):
        continue

# 验证点二：安全调用subprocess获取SUID文件（对应1.2.5节与1.7.2节的注入防护）
result = subprocess.run(
    ["find", "/tmp", "-perm", "-4000", "-type", "f"],
    capture_output=True, text=True, timeout=10
)
print(result.stdout)

# 验证点三：获取监听端口并处理pid为None的情况（对应1.6.6节与1.7.3节）
for conn in psutil.net_connections(kind='tcp'):
    if conn.status == 'LISTEN':
        print(conn.laddr, "PID:", conn.pid if conn.pid else "权限不足/未知")

# 验证点四：输出为规范CSV
with open('/tmp/test_report.csv', 'w', newline='', encoding='utf-8-sig') as f:
    writer = csv.writer(f)
    writer.writerow(['检查项', '结果'])
    writer.writerow(['测试', 'OK'])

验证要点：请以非root权限先运行一次上述脚本，观察psutil.AccessDenied异常的实际触发频率与conn.pid返回None的比例，再以sudo权限重新运行对比差异——这一对比实验将直接印证1.7.3节”巡检脚本必须以root权限运行才能获得完整可见性”这一结论，而非仅停留在理论认知层面。
