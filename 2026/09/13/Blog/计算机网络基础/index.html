1.1 应用层

应用层（Application Layer）：这是网络体系结构中的最顶层，提供用户接口和应用程序之间的通信服务。在这一层，用户可以访问各种网络应用程序，如电子邮件、文件传输和远程登录。

1.1.1 HTTP 协议

HTTP 即超文本传输协议，是万维网服务器响应报文到本地客户端的传输协议；作用于应用层，基于 TCP/IP 协议进行传输，其中 HTTP1.0、HTTP1.1、HTTP2.0 均为 TCP 实现，HTTP3.0 基于 UDP 实现。现主流使用 HTTP1.0 和 HTTP3.0。

工作流程

在本地浏览器中输入一个网址，此时浏览器就会给对应的服务器发送一个HTTP请求，对应的服务器收到这个请求之后，经过计算就会返回一个HTTP响应，并且当我们访问一个网站的时候，可能涉及到不止一次的HTTP请求和相应的交互过程。

URL（统一资源定位符）

URL 格式:

协议://域名:端口/路径?参数#片段

协议即通信协议；域名即 ip 地址的映射；端口即服务器的服务端口，通过特定的端口访问特定的服务；路径即服务器资源的物理路径；参数即为服务器提交数据；片段通常是 HTML 页面，对于长篇幅的页面可以通过提交片段参数来跳转页面；

POST 方法

在HTTP协议中，POST是一种非常常见的请求方法，主要用于向服务器提交数据。与GET请求不同，GET通常用于获取资源，而POST主要用于向服务器发送数据，让服务器根据这些数据执行某些操作。

例如，用户登录网站时，需要将用户名和密码发送给服务器；用户注册账号时，需要提交个人信息；用户上传文件时，需要将文件发送到服务器。这些操作通常都会使用POST请求。

1.1.2 FTP 协议

FTP（File Transfer Protocol，文件传输协议）是一种用于在网络中进行文件传输的应用层协议。它主要用于实现客户端与服务器之间的文件上传、下载以及文件管理操作。

FTP 的工作流程： 客户端首先通过TCP 21端口连接FTP服务器，建立控制连接；随后客户端发送用户名和密码进行身份验证；服务器验证用户身份后，根据用户权限允许执行相应操作；当用户需要上传或下载文件时，FTP会建立数据连接，通过数据连接完成文件传输；传输完成后关闭数据连接，控制连接可以继续保持，用于后续操作。

FTP 基于 TCP/IP 协议负责客户端和服务器之间进行文件操作和通信。FTP通信过程中比较特殊的一点是，它并不是只使用一个连接，而是同时使用两个TCP连接，分别是控制连接和数据连接。

1、 控制连接主要用于传输FTP命令，默认占用 TCP 21 端口。（ 负责发送命令，控制FTP操作 ）

2、 数据连接主要用于实际传输文件内容，例如上传一个图片文件或者下载一个压缩包时，真正的数据会通过数据连接进行传输。传统FTP中数据连接默认使用TCP 20 端口。 （ 负责传输真正的文件数据 ）

FTP的数据传输方式主要分为主动模式（Active Mode）和被动模式（Passive Mode）。

1、主动模式： 主动模式中，客户端首先连接服务器的21端口建立控制连接，然后服务器主动连接客户端建立数据连接。这种方式的问题在于，如果客户端处于防火墙或NAT环境之后，服务器可能无法主动连接客户端，因此实际使用中存在一定限制。

2、被动模式： 被动模式则相反，客户端与服务器建立控制连接后，服务器开放一个随机端口等待客户端连接，由客户端主动建立数据连接。由于客户端主动发起连接，更容易通过防火墙，因此目前互联网环境中被动模式使用更加广泛。

FTP在使用过程中通常需要用户进行身份认证。用户登录时需要提供用户名和密码，服务器根据用户权限决定用户可以执行的操作。例如，普通用户可能只能下载文件，而管理员用户可能拥有上传、删除以及修改文件的权限。

传统FTP协议存在一个严重的安全问题，即数据通常采用明文传输方式。在没有加密的情况下，用户名、密码以及传输的文件内容都可能被攻击者通过抓包工具获取。 除此之外，FTP服务器还可能存在匿名登录、弱密码以及权限配置错误等安全问题。例如，某些FTP服务器允许匿名用户登录，如果服务器权限配置不当，攻击者可能访问敏感文件，甚至上传恶意文件进一步攻击服务器。

提高 FTP 安全性的操作：

1、FTPS（ FTP Secure ）

它是在传统FTP基础上加入SSL/TLS加密，使FTP通信过程中的数据能够被加密传输。

2、SFTP（ SSH File Transfer Protocol ）

SFTP 基于SSH协议实现文件传输，与FTP并不是同一种协议。SFTP默认使用22端口，由于通信过程经过SSH加密，因此安全性更高。

在网络安全学习中，FTP是一个非常重要的基础服务。渗透测试人员在进行信息收集时，经常会检查目标服务器是否开放FTP服务，例如扫描21端口、测试匿名登录、检测弱密码以及分析FTP服务器权限配置。

1.1.3 SMTP 协议

SMTP（Simple Mail Transfer Protocol），即简单邮件传输协议，它是一组用于由源地址到目的地址传送邮件的规则，由它来控制信件的中转方式。SMTP协议属于TCP/IP协议簇，它帮助每台计算机在发送或中转信件时找到下一个目的地。通过SMTP协议，所指定的服务器，就可以把E-mail寄到收信人的服务器上了，整个过程只要几分钟。SMTP服务器则是遵循SMTP协议的发送邮件服务器，用来发送或中转发出的电子邮件。SMTP是一种TCP协议支持的提供可靠且有效电子邮件传输的应用层协议。

1.1.4 POP3 协议

 POP3（Post Office Protocol Version 3，邮局协议第三版）是一种用于**接收电子邮件**的应用层协议，主要作用是帮助用户从邮件服务器中获取邮件。它规定了邮件客户端与邮件服务器之间的通信方式，使用户能够通过邮件客户端查看和管理存储在邮件服务器中的电子邮件。
POP3 的工作过程主要分为三个阶段：

首先，邮件客户端通过网络连接邮件服务器，并使用用户名和密码进行身份认证。认证成功后，客户端进入邮件访问状态。

其次，客户端向邮件服务器发送邮件获取请求，将服务器中保存的邮件下载到本地设备。POP3 默认会将邮件下载到客户端进行管理，用户可以在本地查看邮件内容。

最后，邮件客户端断开与服务器的连接，结束邮件接收过程。根据客户端设置的不同，服务器上的邮件可以选择保留或删除。

POP3 协议采用 **TCP 协议**进行通信，默认使用 **110 端口**；当启用 SSL/TLS 加密时，通常使用 **995 端口**，用于提高邮件传输过程中的安全性。

POP3 的主要特点是邮件下载到本地进行管理，因此用户可以离线查看已经下载的邮件。但是，由于邮件主要存储在客户端设备中，当用户在多个设备之间切换时，邮件同步效果较差。

与 IMAP 协议相比，POP3 更注重邮件的下载和本地存储，而 IMAP 更注重邮件服务器端管理和多设备同步。例如，使用 POP3 收取邮件后，在手机上读取的邮件状态可能不会同步到电脑；而 IMAP 会实时同步邮件的阅读状态、文件夹等信息。

POP3 主要应用于传统电子邮件客户端中，例如 Outlook、Foxmail 等邮件管理软件。随着移动互联网的发展，由于 IMAP 在多设备环境下具有更好的同步能力，目前许多邮箱服务更推荐使用 IMAP 协议。

1.1.5 DNS

DNS（Domain Name System，域名系统）是一种用于将域名转换为 IP 地址的应用层协议，主要作用是解决用户难以记忆复杂 IP 地址的问题。它规定了客户端与 DNS 服务器之间的通信方式，使用户可以通过输入简单易记的域名访问对应的网络资源。

在互联网中，计算机之间通信依靠 IP 地址进行定位，例如访问服务器需要知道服务器的 IP 地址。但是 IP 地址由数字组成，难以记忆，因此 DNS 提供了一种域名解析机制，将类似 www.example.com 这样的域名转换为对应的 IP 地址，使用户能够通过域名访问目标服务器。

DNS 工作时，用户在浏览器中输入域名后，操作系统首先查询本地 DNS 缓存，如果缓存中存在对应记录，则直接返回 IP 地址；如果不存在，则向 DNS 服务器发送查询请求。DNS 服务器根据域名逐级查询，最终找到对应的 IP 地址，并返回给客户端。客户端获得 IP 地址后，就可以根据该地址与目标服务器建立连接。

DNS 采用分布式数据库结构，全球 DNS 服务器按照层级组织，主要包括：

  • 根域名服务器（Root DNS Server）：负责管理顶级域名服务器的信息，是 DNS 查询的最高层。
  • 顶级域名服务器（TLD Server）：负责管理 .com、.cn、.org 等顶级域名。
  • 权威域名服务器（Authoritative DNS Server）：保存具体域名与 IP 地址的对应关系，提供最终解析结果。
  • 本地 DNS 服务器（Local DNS Server）：通常由网络运营商或企业提供，负责代理用户的 DNS 查询。

DNS 查询方式主要分为两种：

递归查询（Recursive Query）：客户端向 DNS 服务器发送请求后，由 DNS 服务器负责完成整个查询过程，并直接返回最终结果。用户设备通常采用这种方式。

迭代查询（Iterative Query）：DNS 服务器之间进行查询时采用这种方式，每个 DNS 服务器只返回下一步应该查询的服务器地址，由请求方继续查询。

DNS 默认使用 UDP 协议的 53 端口进行通信，因为 DNS 查询数据量较小，使用 UDP 可以降低通信开销，提高查询效率。当 DNS 数据较大或需要进行区域传输时，也会使用 TCP 协议的 53 端口。

DNS 常见记录类型包括：

  • A 记录：将域名解析为 IPv4 地址。
  • AAAA 记录：将域名解析为 IPv6 地址。
  • CNAME 记录：域名别名，将一个域名指向另一个域名。
  • MX 记录：指定邮件服务器地址，用于电子邮件系统。
  • NS 记录：指定负责解析该域名的 DNS 服务器。

DNS 是互联网基础设施的重要组成部分，它隐藏了底层 IP 地址，使用户能够通过易记的域名访问互联网资源。同时，DNS 也涉及网络安全问题，例如 DNS 劫持、DNS 欺骗等攻击方式，因此现代网络中通常会使用 DNSSEC、DoH（DNS over HTTPS）等技术增强 DNS 查询的安全性。

1.1.6 DHCP

DHCP（Dynamic Host Configuration Protocol，动态主机配置协议）是一种用于自动分配网络配置参数的应用层协议，主要作用是帮助网络中的设备自动获取 IP 地址、子网掩码、默认网关、DNS 服务器地址等网络信息。它规定了客户端与 DHCP 服务器之间的通信方式，使设备接入网络时无需手动配置网络参数即可正常通信。

在传统网络环境中，每台设备连接网络时都需要手动设置 IP 地址、子网掩码、网关等信息，不仅操作复杂，而且容易出现 IP 地址冲突问题。DHCP 通过自动化配置机制解决了这些问题，使大量设备能够快速接入网络。

DHCP 的工作过程通常被称为 DORA 过程，包括四个步骤：

1. DHCP Discover（发现阶段）

当客户端设备接入网络时，由于还没有 IP 地址，因此会以广播方式发送 DHCP Discover 报文，寻找网络中的 DHCP 服务器。

2. DHCP Offer（提供阶段）

DHCP 服务器收到 Discover 请求后，会从地址池中选择一个可用 IP 地址，并向客户端发送 DHCP Offer 报文，提供 IP 地址以及相关网络配置参数。

3. DHCP Request（请求阶段）

客户端收到多个 DHCP Offer 后，会选择其中一个服务器提供的配置，并发送 DHCP Request 报文，请求使用该 IP 地址，同时通知其他 DHCP 服务器放弃分配。

4. DHCP ACK（确认阶段）

DHCP 服务器收到 Request 请求后，会发送 DHCP ACK 确认报文，将 IP 地址正式分配给客户端。客户端收到确认后，即可使用该 IP 地址访问网络。

DHCP 协议采用 UDP 协议进行通信，其中：

  • DHCP 客户端使用 68 端口
  • DHCP 服务器使用 67 端口

由于客户端在初始阶段还没有 IP 地址，因此 DHCP 通常通过广播方式进行通信，使客户端能够发现局域网中的 DHCP 服务器。

DHCP 分配的 IP 地址通常不是永久固定的，而是具有一定的租期（Lease Time）。客户端在租期即将结束时，可以向 DHCP 服务器发送请求进行续租，以继续使用该 IP 地址。如果设备断开网络并且租期过期，该 IP 地址可以被 DHCP 服务器重新分配给其他设备。

DHCP 主要由以下几个部分组成：

  • DHCP 客户端（Client）：需要获取网络配置的设备，例如电脑、手机等。
  • DHCP 服务器（Server）：负责管理 IP 地址池，并向客户端分配网络参数。
  • IP 地址池（Address Pool）：DHCP 服务器可以分配的 IP 地址范围。

DHCP 是现代网络中非常重要的基础协议，广泛应用于家庭网络、企业局域网以及无线网络环境中。它降低了网络管理难度，提高了 IP 地址利用率，使大量设备能够快速、自动地连接互联网。

1.1.7 SSH

SSH（Secure Shell，安全外壳协议）是一种用于远程登录和安全通信的应用层协议，主要作用是在不安全的网络环境中，为用户提供安全的远程访问方式。它规定了客户端与服务器之间如何建立加密连接，使用户能够远程管理服务器、执行命令以及传输文件。

在传统网络环境中，远程登录通常使用 Telnet 协议，但是 Telnet 采用明文传输方式，用户的账号、密码以及通信内容都可能被攻击者窃取。SSH 通过加密技术解决了这一安全问题，使远程管理更加安全可靠，因此目前广泛应用于 Linux 服务器管理、云服务器运维以及网络设备管理等场景。

SSH协议主要由三个组件组成：SSH客户端、SSH服务器和SSH协议本身。客户端负责发起连接请求，服务器负责处理请求并提供服务，而SSH协议则定义了客户端和服务器之间的通信规则。

SSH 的工作过程主要包括以下几个阶段：

1. 建立连接阶段

客户端向服务器发起 SSH 连接请求，服务器收到请求后返回自身信息。双方通过协商确定使用的加密算法和通信参数，为后续安全通信建立基础。

2. 身份认证阶段

客户端需要向服务器证明自己的身份，常见认证方式包括：

  • 密码认证：用户输入用户名和密码进行验证。
  • 密钥认证：客户端使用私钥进行身份验证，服务器保存对应的公钥。相比密码认证，密钥认证更加安全，常用于服务器管理。

3. 加密通信阶段

身份验证成功后，客户端与服务器之间建立加密通道，之后传输的数据都会经过加密处理，包括执行的命令、返回结果以及文件传输内容，从而防止数据被窃听或篡改。

SSH 主要基于 TCP 协议进行通信，默认使用 22 端口。

SSH 协议主要包含以下功能：

  • 远程登录：用户可以通过 SSH 登录远程服务器，并执行命令。例如通过 SSH 管理云服务器。
  • 安全文件传输：SSH 可以通过 SCP、SFTP 等方式实现文件的安全传输。
  • 远程命令执行：用户可以直接在本地执行远程服务器上的命令。
  • 端口转发：SSH 可以建立安全隧道，实现数据转发，例如访问内网服务。

SSH 常见应用场景包括：

  • Linux 云服务器远程管理；
  • 企业服务器维护；
  • 网络设备远程配置；
  • 软件开发中的代码部署；
  • 运维人员进行系统管理。

例如，用户购买云服务器后，通常通过 SSH 登录服务器：

连接成功后，即可在本地终端操作远程 Linux 系统。

SSH 与 Telnet 最大的区别在于安全性：

SSH 是现代互联网基础设施中非常重要的安全协议，尤其是在云计算环境中，几乎所有 Linux 服务器都依靠 SSH 进行远程管理。通过 SSH，管理员可以安全地控制远程主机，是网络运维、服务器开发以及网络安全学习中的基础技术。

1.2 表示层

表示层负责处理数据的语法和语义，确保一个系统应用层发出的信息能被另一个系统的应用层正确理解。

表示层是 OSI七层模型中的第六层（Layer 6）它主要负责解决不同计算机系统之间数据格式不一致的问题，保证应用程序能够正确理解和使用传输过来的数据。

简单来说：表示层负责“数据怎么表示”，让不同系统之间的数据能够被正确识别、读取和处理。

如果把网络通信比作人与人交流：

  • 应用层负责“说什么内容”
  • 表示层负责“用什么语言表达、如何编码、如何加密”
  • 会话层负责“建立和维护交流过程”

1.3 会话层

会话层是 OSI七层模型中的第五层（Layer 5）。会话层主要负责管理两个网络应用程序之间的通信会话（Session），包括建立会话、维持会话、同步通信状态以及结束会话。

会话层负责“管理一次通信过程”，决定双方什么时候开始通信、如何保持通信、什么时候结束通信。

如果把网络通信比作人与人打电话：

1.4 传输层

传输层是 OSI七层模型中的第四层（Layer 4），传输层是整个网络通信中非常重要的一层，它负责实现端到端（End-to-End）的数据传输，解决数据如何从一个应用程序可靠地传输到另一个应用程序的问题。

简单来说：传输层负责“数据怎么从一个程序准确、高效地传送到另一个程序”。

如果把网络通信比作寄快递：

  • 网络层：负责找到城市和路线
  • 数据链路层：负责局域网内传递
  • 物理层：负责真正发送信号

IPv4 地址与二进制基础

一、IPv4 地址的基本结构

IPv4 地址长度为 32 比特，分为 4 字节，每字节 8 比特，每组取值范围为 0 到 255。点分十进制记法（如 192.168.1.100）是为便于人类阅读而设计的表示方式。

二、计算机视角的 IPv4 地址

计算机实际处理的是对应的 32 位二进制形式。例如，192.168.1.100 在计算机眼中为 11000000.10101000.00000001.01100100。每组 8 比特称为一个八位组，全 0 对应十进制 0，全 1 对应十进制 255，因此每段最大值为 255。

三、十进制与二进制的转换方法

每个八位组的二进制位从高位到低位分别对应 128、64、32、16、8、4、2、1。将十进制数拆分为上述权值的和，对应位置写 1，其余写 0。例如，192 = 128 + 64，对应二进制 11000000；168 = 128 + 32 + 8，对应二进制 10101000。

四、前缀长度与网络部分的区分

斜杠后缀（如 /24）不属于 IP 地址本身，而是用于指示前多少比特属于网络部分，该内容在子网掩码部分展开。理解 IP 地址的二进制本质是掌握子网掩码、CIDR、路由原理以及网安工具（如 Nmap 扫描范围）的基础。

子网掩码与网络划分

一、子网掩码的作用

IP 地址本身无法区分哪部分是网络、哪部分是主机，子网掩码用于明确这一边界。子网掩码为 32 位，与 IP 地址等长，其中二进制 1 对应网络部分，0 对应主机部分。例如，255.255.255.0 的二进制前 24 位为 1，表示前 24 位是网络部分，后 8 位是主机部分。

二、CIDR 表示法

子网掩码中 1 的个数可用前缀长度表示，如 255.255.255.0 等效于 /24，称为 CIDR 表示法。因此，192.168.1.100/24 表示该 IP 的前 24 位为网络部分，后 8 位为主机部分，即网络为 192.168.1，主机为 100。

三、地址数量与特殊地址

主机位为 n 时，该子网总地址数为 2^n。其中，主机位全 0 的地址为网络地址（如 192.168.1.0），主机位全 1 的地址为广播地址（如 192.168.1.255），这两个地址不能分配给主机，因此可用主机数为 2^n - 2。例如，/24 子网有 8 个主机位，总地址 256 个，可用主机为 254 个（192.168.1.1 至 192.168.1.254）。

四、前缀长度与子网大小的关系

前缀长度越大，网络部分越长，主机部分越短，子网越小，可用主机数越少。如 /8 有 2^24 个地址，/16 有 2^16 个，/24 有 2^8 个，/28 只有 2^4 个。这一规律是理解网段划分和网络安全工具（如 Nmap 扫描范围）的基础。

我们以“你用电脑通过浏览器访问 www.baidu.com 并打开百度首页”为例，完整拆解 TCP/IP 四层模型在实际场景中的协作流程——从你输入网址按下回车，到网页显示在屏幕上，每一层都在执行专属任务，且严格遵循“上层依赖下层、下层为上层服务”的逻辑。

2.1.1 访问网页的本质

访问百度首页，本质是“你的电脑（客户端）向百度的服务器（服务端）发送‘请求数据’，百度服务器接收后返回‘网页数据’（文字、图片、代码等），你的电脑接收并解析数据后显示网页”。整个过程需经过“客户端四层打包→网络传输→服务端四层解包→服务端四层打包→网络传输→客户端四层解包”六个关键阶段，我们分阶段拆解。

当你输入 www.baidu.com 并按下回车，浏览器（如Chrome）会先触发“请求百度服务器”的指令，数据从 应用层开始向下传递，每经过一层就“加一层包装（头部信息）”，最终变成能在物理网络中传输的信号。

阶段一：客户端“请求报文”打包

1.应用层：生成“访问网页的请求数据”
  • 任务：处理“用户需求”（访问百度首页），生成符合“网页访问协议”的数据。
  • 具体操作：
    • 浏览器最初需要将“访问百度”的需求，转换成HTTP协议（应用层核心协议，专门用于网页传输）的“请求报文”。
    • 这个请求报文包含关键信息：
      • 请求方法：GET（表示“获取数据”，即获取百度首页的HTML代码）；
      • 目标地址：www.baidu.com（但应用层不认识域名，会先调用 DNS协议把域名解析成百度服务器的IP地址，比如 180.101.49.11——这一步是应用层的“前置任务”）；
      • 请求头：包含浏览器类型（如Chrome）、协助的文件格式（如HTML、JPG）等；
      • 空行+请求体：访问首页无额外参数，请求体为空。
  • 输出：HTTP请求报文（应用层数据，还不能直接传输）。
2. 传输层：给请求数据“加追踪规则（TCP头部）”
  • 任务：确保“应用层数据”能“可靠、有序”地传到百度服务器（因为网页数据不能丢包，否则页面会错乱），所以用TCP协议 处理。
  • 具体操作：
    • 传输层接收应用层的HTTP请求报文后，先给它“加一个TCP头部”（相当于给包裹贴“追踪单”），头部包含：
      • 源端口：你电脑浏览器的临时端口（如 54321——每个应用的网络连接都有唯一端口，确保服务器返回的数据能准确回到Chrome，而不是微信）；
      • 目的端口：百度服务器的“HTTP服务端口”（默认 80——服务器会监听 80 端口，接收所有网页访问请求）；
      • 序列号（Seq）：给数据分配唯一编号（如 12345），确保服务器接收时能按顺序拼接（避免数据乱序）；
      • 确认号（Ack）：初始为 0（后续通信中用于“确认收到数据”）。
    • 若HTTP请求报文较大（比如带了复杂参数），传输层会将其拆分成多个“TCP段”（小数据包），每个段都加独立的TCP头部。
  • 输出：TCP段（TCP头部 + HTTP请求报文）。
3. 网络层：给TCP段“加地址（IP头部）”，规划传输路线
  • 任务：给“TCP段”加“目标地址”，并确定“从你的电脑到百度服务器”的传输路线。
  • 具体操作：
    • 网络层接收TCP段后，加一个IP头部（相当于给包裹贴“收件地址”），头部囊括：
      • 源IP地址：你电脑的公网IP（如 113.207.56.78——由你的运营商分配，是你电脑在互联网中的“身份证”）；
      • 目的IP地址：百度服务器的公网IP（如 180.101.49.11——通过DNS解析得到）；
      • 生存时间（TTL）：限制数据包最多经过的路由器数量（如 64，避免数据包在网络中无限循环）。
    • 同时，网络层的路由器（你家路由器或运营商路由器）会通过“路由协议”（如BGP）规划路线：比如你的数据从“家→小区交换机→运营商机房→全国骨干网→百度服务器机房”。
  • 输出：IP数据包（IP头部 + TCP段）。
4. 链路层：给IP数据包“加硬件地址（链路层头部）”，转成物理信号
  • 任务：将“IP数据包”转换成能在物理介质（网线、Wi-Fi）中传输的信号，并依据硬件设备转发。
  • 具体操作：
    • 链路层接收IP数据包后，加一个链路层头部（如以太网头部），含有：
      • 源MAC地址：你电脑网卡的硬件地址（如 00:1A:2B:3C:4D:5E——每个网卡的MAC地址全球唯一，是“设备的硬件身份证”）；
      • 目的MAC地址：下一跳设备的MAC地址（比如你家路由器的MAC地址——链路层只负责“相邻设备”的通信，不认识远隔千里的百度服务器，因而先传给路由器）。
    • 最终，链路层将“链路层帧”（链路层头部 + IP数据包）转换成电信号（网线）或 无线电波（Wi-Fi），通过物理介质传输到下一跳设备（你家路由器）。
  • 输出：链路层帧（电信号/无线电波形式）。

阶段二：网络传输

  • 你的电脑发送的“链路层帧”，会通过路由器层层转发：先到你家路由器，再到小区交换机，接着进入运营商的核心机房，通过“全国骨干网”（光纤）传输到百度服务器所在的机房，最后到达百度的路由器，再转发到百度的服务器。
  • 转发过程中，只有链路层的MAC地址会不断变化（每到一个路由器，就更新“下一跳MAC地址”），而IP头部的源IP、目的IP始终不变（确保最终能找到百度服务器）。

阶段三：服务器”请求报文“解包

百度服务器接收到底层传来的“链路层帧”后，会从链路层开始向上传递，每经过一层就“拆掉一层包装（头部信息）”，最终拿到应用层的“HTTP请求报文”，理解“用户要访问首页”的需求。

1. 链路层：接收物理信号，拆链路层头部
  • 百度服务器的网卡接收电信号/光信号，转换成“链路层帧”，拆掉“链路层头部”，提取出“IP数据包”，传递给网络层。
2. 网络层：拆IP头部，确认目标地址
  • 拆掉“IP头部”，检查“目的IP地址”是否是自己的IP（确认数据没发错），提取出“TCP段”，传递给传输层。
3. 传输层：拆TCP头部，确认端口和数据完整性
  • 拆掉“TCP头部”，通过“目的端口（80）”将数据分配给服务器上的“HTTP服务进程”（百度专门处理网页请求的程序），同时通过“序列号”确认TCP段完整、有序，提取出“HTTP请求报文”，传递给应用层。
4. 应用层：解析HTTP请求，生成响应数据
  • 百度服务器的HTTP服务进程解析HTTP请求报文，知道“用户要获取首页数据”，于是生成“HTTP响应报文”——包含百度首页的HTML代码、CSS样式、图片链接等数据，传递给传输层，准备返回给你的电脑。

阶段四：服务器“响应报文”四层打包

这个过程和“客户端打包请求数据”完全对称：

  • 应用层的HTTP响应报文 → 传输层加TCP头部（源端口80，目的端口54321）→ 网络层加IP头部（源IP180.101.49.11，目的IP113.207.56.78）→ 链路层加MAC头部，转成物理信号，通过网络传回你的电脑。

阶段五：网络传输

  • 百度服务器生成响应数据后，会先发送给百度机房内的交换机和路由器，经过百度出口路由器离开服务器所在的数据中心，进入运营商的骨干网络，通过全国高速光纤链路传输到你所在地区的运营商核心机房，再经过城域网传输到你所在小区的交换机，最后到达你家路由器。你的电脑接收到路由器转发来的链路层帧，经过网卡解封装，最终获得百度服务器返回的数据。
  • 转发过程中，只有链路层的MAC地址会不断变化（每到一个路由器，就更新“下一跳MAC地址”），而IP头部的源IP、目的IP始终不变（确保最终能找到客户端）。

阶段六：客户端解包

你的电脑接收百度服务器返回的“链路层帧”后，再次从链路层到应用层拆包：

  • 链路层拆MAC头部 → 网络层拆IP头部 → 传输层拆TCP头部（按序列号拼接信息）→ 应用层拆HTTP响应报文，拿到百度首页的HTML、CSS、图片材料。
  • 最后，浏览器解析这些数据：渲染HTML结构、加载CSS样式、下载图片，最终将完整的百度首页呈现在你的电脑屏幕上。

3 HTTP/HTTPS 协议

HTTP协议，全称超文本传输协议（英文：HyperText Transfer Protocol）是一种使用非常广泛的用于分布式、协作式和超媒体信息系统的应用层协议。HTTP是万维网的数据通信的基础。为什么称之为超文本传输协议呢，不知道大家还记不记得我之前给大家讲前端技术的时候提到过前端页面骨架是HTML语言写出来的，HTML全称为超文本标记语言，HTTP协议最开始就是为了传输HTML页面数据来制定的一种协议。设计HTTP最初的目的为了提供一种发布和接收HTML页面的方法。

简单来说就是（可略过）：HTTP的发展是由蒂姆·伯纳斯·李于1989年在欧洲核子研究组织（CERN）所发起。HTTP的标准制定由万维网协会（World Wide Web Consortium，W3C）和互联网工程任务组（Internet Engineering Task Force，IETF）进行协调，最终发布了一一系列的RFC，其中最有名的是1999年6月公布的RFC 2616，定义了HTTP协议中现今广泛使用的一个版本——HTTP 1.1，在这之前应用广泛的是HTTP 1.0版本。2014年12月，互联网工程任务组（IETF）的Hypertext Transfer Protocol Bis（httpbis）工作组将HTTP/2标准提议递交至IETF进行讨论，于2015年2月17日被批准。HTTP/2标准于2015年5月以RFC 7540正式发布，取代HTTP 1.1成为HTTP的实现标准。但实际上到目前为止，广泛使用的还是HTTP 1.1版本。

3.1 HTTP 协议格式

HTTP协议遵循标准的请求-响应（Request-Response）模型：
请求：客户端通过HTTP协议主动向服务器发送请求。
响应：服务器收到客户端发来的请求后进行处理，并将结果作为响应返回给客户端。

HTTP协议具有两个显著特点：
无连接：每一次请求都想要建立一个新的连接，处理完既断开
无状态：服务器不会保存客户端的状态信息。这意味着对于服务器而言，每一次请求都是全新的，它不具有记忆功能。

请求行：请求方法(GET) 空格 URI(资源地址) 空格 HTTP版本(HTTP/1.1) 换行符(\r\n)

请求报头：表示请求的属性。冒号分割的键值对；每组属性之间使用 \r\n 分隔，遇到空行表示Header部分结束。

请求正文：空行后面就是请求正文，请求正文允许为空！但如果有内容，在请求报头中就必须有 Content-Length属性的报头来标记正文长度。

响应格式

状态行：HTTP版本(HTTP/1.1) 空格 状态码 空格 状态码描述符 换行符(\r\n)

响应报头：表示响应的属性。冒号分割的键值对；每组属性之间使用 \r\n 分隔，遇到空行表示结束。

响应正文：空行后面就是响应正文，可以为空！但如果有内容，在响应报头中就必须有 Content-Length属性的报头来标记正文长度。

Http 的请求方法

状态码 英文名称 含义（通俗版） 常见场景
200 OK 成功 最常见的，表示你的请求服务器收到了，也没出问题，东西给你拿回来了。
301 Moved Permanently 永久重定向 比如网站换网址了，收藏夹里的旧链接会自动跳到新链接。

3.3 Cookie

3.3.1 定义与本质

Cookie：服务器通过 HTTP 响应（Set-Cookie）指示浏览器保存的一小段数据，浏览器在后续符合条件的 HTTP 请求（Cookie）中自动回传。

  • Set-Cookie：仅出现在 Response
  • Cookie：仅出现在 Request
  • 二者方向不可混淆

本质：Cookie 是客户端状态存储机制，是 HTTP 无状态特性的补充手段，本身不等于 Session、不等于身份认证、不等于加密。

3.3.2 存在动因：弥补 HTTP 无状态

    HTTP 协议本身不维护请求间关联，服务器无法仅凭 IP 判断”是否为同一用户”。Cookie 提供了跨请求的客户端标识携带能力，使服务器能够关联多次请求。

3.3.3 核心工作闭环（以登录为例）

关键认知：Cookie 是客户端持有的”编号”，Session 是服务器端持有的”记录”。

3.4 Session

3.4.1 定义与本质

Session的本质就是服务器端用于保存某个用户/客户端会话状态的机制。

Cookie和Session的区别

Cookie的工作流程：

    Session就是服务器端保存的、以 Session ID 为键、以会话状态数据为值的一组键值记录。session id也就是服务器与客户端之间用于”认领会话”的唯一索引键——客户端持有它，服务器用它反查对应的会话状态。服务端在登录成功后生成 Session ID，通过 Response 的 Set-Cookie 下发给客户端；客户端保存后，后续请求由浏览器自动携带该 Cookie。服务端收到后，以 Session ID 为键查会话存储，识别用户身份与会话状态——这一步是会话识别，而非重新认证。

  • Session 是逻辑概念，不是特指某一种存储
  • Session 本身不等于 Cookie、不等于 Token、不等于认证

3.4.2 存在动因：弥补 HTTP 无状态

HTTP 请求间无天然记忆关系。服务器无法仅凭 IP 判断”是否为同一用户”。Session 机制人为建立：

3.4.3 完整工作流程

    服务端在登录时验证用户名与密码完成认证，认证成功后创建会话、生成高熵随机的 Session ID，并以键值形式将用户身份与会话状态（如 user_id、登录状态、角色等）存入服务端的 Session Store；随后服务端通过 Response 的 Set-Cookie 将该 Session ID 下发给客户端，浏览器按 Cookie 规则保存（通常带 Secure、HttpOnly、SameSite 等安全属性）；此后客户端在后续请求中由浏览器自动携带该 Cookie（出现在 Request 中），服务端收到后以 Session ID 为键查询 Session Store，识别会话、恢复用户身份（这一步是会话识别，而非重新认证），再依据会话中的角色与权限完成授权判断，最终返回对应资源——由此实现”HTTP 无状态之上的有状态会话”。

这是传统 Cookie + Session 登录机制的标准闭环。

3.5 Authentication and Authorization

3.5.1 认证验证（Authentication）

Authentication（AuthN） 是验证主体（Subject）身份真实性的过程。

核心问题：

Who are you?——你是谁？

服务器通过某种**身份凭证（Credential）**验证客户端声明的身份。

常见认证凭证：

  • 用户名 + 密码
  • Session ID
  • API Key
  • Access Token
  • JWT
  • 数字证书
  • 多因素认证凭证

认证基本流程

****以用户名密码登录为例：
Client │ │ username + password ▼Server │ ├─ 查询用户 ├─ 验证密码 │ ▼Authentication Success │ ▼建立已认证状态

认证成功后，服务器建立或确认一个已认证身份（Authenticated Identity）。

例如：
User ID = 10001 Username = zhangsan Authenticated = true

后续请求必须能够向服务器证明：

当前请求属于已经通过认证的 User 10001。

这就是 Session、Token 等机制发挥作用的地方。

3.5.2 授权验证（Authorization）

Authorization（AuthZ） 是在主体身份确定之后，判断该主体是否具有执行某项操作、访问某个资源的权限。

核心问题：

What are you allowed to do?——你能做什么？

例如：
User 10001 │ ├── GET /profile → 允许 ├── POST /comment → 允许 ├── DELETE /user/10002 → 拒绝 └── GET /admin/users → 拒绝

这里服务器已经知道：
你是谁 = User 10001

但是：
你是否有权限执行这个操作？

属于 Authorization。

3.6.3 Token 的存储与安全

Token 本质上是一种身份凭证。

因此不能把它当普通字符串处理。

如果：
Token = abc123

服务器只要接受：
Authorization: Bearer abc123

就能代表某个用户进行操作，那么：
abc123

本身就相当于一把“临时身份钥匙”。

客户端存储

常见位置包括：
Cookie
Web Storage
内存
移动端安全存储

不同存储方式有不同安全特性。

例如 Cookie 可以使用：
Secure
HttpOnly
SameSite

降低某些攻击风险。

但是：

HttpOnly 只能限制 JavaScript 对 Cookie 的直接读取，并不能让 Token 本身变得安全。

如果攻击者已经能够利用浏览器环境直接代表用户发送请求，HttpOnly 也不能解决所有问题。

服务端存储

Token 是否需要服务端保存取决于 Token 类型和系统设计。

例如一种传统的随机 Token：
Token = 8f3a…

服务器保存：
8f3a… → User 10001

那么服务器可以通过 Token 查找用户。

这种方式本质上仍然具有服务端状态。

而某些自包含 Token：
Token
↓
自身携带 Claims
↓
服务器验证签名

服务器可能不需要查询对应的 Session 数据。

这就是为什么后面学习 JWT 时会涉及：

有状态 Token 与无状态 Token

但现在你只需要知道：

Token ≠ 必然无状态。

3.6.4 Token 泄露、劫持与重放

这是网络安全学习 Token 时非常重要的一部分。

Token 泄露

Token 被未经授权的第三方获得。

例如：
合法用户
↓
Token
↓

↓
Token 泄露

那么攻击者可能在 Token 有效期内冒充该用户。

Token 劫持

Token Hijacking 通常指攻击者获取并利用合法用户 Token，以冒充该用户。

它和你之前学习的：

Session Hijacking

本质上属于相似的安全问题。

↓

↓
窃取 Token

Token Replay：重放

假设合法请求：

攻击者截获：
ABC123

然后再次发送：

Authorization: Bearer ABC123

服务器如果仍然接受：
ABC123

这就是典型的：

Replay（重放）

这里有一个很重要的认识：

Token 加密并不能自动解决重放问题。

因为攻击者不需要理解 Token 内容。

他只需要：
拿到合法 Token
↓

因此防护重放需要结合具体协议和架构，例如：

  • 短生命周期

  • Token 撤销机制

  • Nonce

  • 请求签名

  • 时间戳

  • Token 与客户端/设备绑定

  • TLS 防止传输过程中被窃取

具体使用哪种方案取决于系统设计。

Token 阶段的验收标准

你现在至少应该能够准确回答：

  1. Token 是什么？
    Token 是一种用于证明或传递身份、权限或授权状态的凭证。在 Web 认证中，通常由服务器签发，客户端在后续请求中携带。

  2. Token 在 Authentication 中解决什么问题？
    解决用户完成一次身份认证后，后续请求如何持续证明自身身份的问题。客户端无需每次重新提交用户名和密码，只需携带有效 Token。

  3. Token 是怎么生成和验证的？
    服务器在认证成功后生成并签发 Token。客户端提交 Token 后，服务器根据 Token 的实现方式进行验证，例如查询服务端存储记录、验证签名、检查有效期和签发方等。

  4. Authorization: Bearer xxx 中的 Bearer 和 Token 分别是什么？
    Bearer 是 HTTP Authorization Header 中的一种认证方案；Token 是实际的认证凭证。
    例如：
    Authorization: Bearer abc123
    Bearer = 认证方案
    abc123 = Token

  5. Token 可以放 Cookie 吗？
    Cookie 是 HTTP 状态管理机制，用于在客户端存储数据，并在符合条件的后续请求中自动携带。Cookie 可以保存 Session ID，也可以保存 Token。

  6. Token 是否一定无状态？
    不一定。
    有状态 Token：服务器保存 Token 与用户状态的映射。
    无状态 Token：Token 自身携带可验证信息，服务器主要通过验证 Token 判断身份，例如常见的 JWT。

  7. Token 为什么属于敏感身份凭证？
    因为服务器可能仅凭有效 Token 就确认请求者的身份或授权状态。攻击者获得有效 Token 后，可能无需密码即可冒充对应用户。

  8. Token 泄露后为什么可能导致身份冒充？
    如果攻击者获得仍然有效的 Token，并且系统没有额外的绑定或防护机制，攻击者可以在有效期内携带该 Token 访问受保护资源，从而造成身份冒充。

  9. 什么是 Token Replay？
    Token Replay（令牌重放）是攻击者获取合法 Token 后，将该 Token 原样重新用于后续请求的攻击方式。
    核心不是破解或修改 Token，而是重复使用合法凭证。

  10. Token、Session、Cookie 三者到底是什么关系？
    Cookie：客户端侧的存储/传输机制。
    Session：服务器侧的会话状态管理机制。
    Token：用于证明或传递身份、权限或授权状态的凭证。
    典型组合：
    Cookie → Session ID → Server Session
    也可以：
    Authorization Header → Token
    或者：
    Cookie → Token
    三者不是同一层面的概念。

  11. 为什么 JWT 是 Token 的一种，而不是 Token 的同义词？
    Token 是“凭证”这一抽象概念；JWT（JSON Web Token）是一种具体的结构化 Token 格式。

    关系：
    Token
    → JWT、随机 Token、API Token 等

    因此：
    JWT ⊂ Token

    JWT 的典型结构是：
    Header.Payload.Signature

这 11 个问题能答清楚，就可以进入 JWT，而不用再继续扩展 Token 的理论。

这份划分更符合当前《网安学习计划纲领》的实际目标。前面给出的 3.7 JWT 结构偏向“完整 JWT 教材”，范围确实超过了当前阶段需要掌握的深度。

结合当前路线，JWT 应该定位为：

HTTP 认证体系中的一个核心令牌机制，以“结构 → 验证 → 信任 → 安全风险”为主线，服务于后续 Web 安全与安全分析学习。

3.7 JWT（JSON Web Token）

3.7.1 JWT 的概念与结构

1. JWT 的定义

JWT（JSON Web Token）是由 RFC 7519 定义的一种开放标准，用于以紧凑（Compact）、URL 安全（URL-safe）的形式表示 Claims（声明）。

JWT 本质上是一种结构化 Token 格式。它允许认证系统将与主体、令牌生命周期以及授权上下文有关的信息封装在 Token 中，并通过数字签名等密码学机制对其进行保护。

因此需要区分：

JWT 是 Token 的一种具体表示格式，而不是认证协议本身。

JWT 常用于：

  • 身份认证；

  • API 访问凭证；

  • 授权信息传递。

2. JWT 的基本结构

典型的签名 JWT 由三个部分组成：
Header.Payload.Signature

三个部分分别承担不同职责：

部分 内容 主要作用
Header 类型、算法等元数据 描述 Token 的保护方式
Payload Claims 承载声明信息
Signature 签名结果 验证内容完整性及签发者可信性

其中：

Header：标题，描述 JWT 使用的密码学算法以及相关元数据。

Payload：承载 Claims。

Signature：对 Header 与 Payload 进行密码学保护后的结果。

3. Self-contained Token

JWT 的重要特征之一是 Self-contained（自包含）。

所谓自包含，是指 Token 本身可以携带完成验证和建立认证上下文所需的部分信息，而不必仅依赖一个服务器端 Session ID。

典型结构：
JWT
├── Header
├── Claims
└── Signature

这与传统 Session 模型形成明显区别：
Session：
Session ID
     ↓
Server-side

        ↓ Session

    User State

而 JWT 可以形成：
JWT
↓
Signature Verification
↓
Claims
↓
Authenticated Principal

但必须注意：

Self-contained ≠ Automatically Trusted

JWT 中的数据只有在完成正确的签名验证、Claims 验证以及应用层安全策略检查后，才能进入认证上下文。

3.7.2 JWT 的编码与签名原理

1. Base64URL

JWT 的 Header 和 Payload 通常经过 Base64URL Encoding。

Base64URL 的作用是：

将二进制或 JSON 数据转换为适合在 URL、HTTP Header 等环境中传输的字符串形式。

Base64URL：

  • 不提供加密；

  • 不提供完整性保护；

  • 不提供身份认证；

  • 不提供机密性。

因此：

Base64URL 是编码，不是密码学保护。

2. Signature

对于典型 JWS JWT，签名输入为：
Base64URL(Header) + “.” + Base64URL(Payload)

随后使用指定算法和密钥生成 Signature。

验证过程使用相应的验证密钥重新计算或验证该签名。

如果 Header 或 Payload 被修改：
原始 Header + 原始 Payload
↓
Signature

变成：
修改后的 Header + 修改后的 Payload
↓
原 Signature

则通常无法通过签名验证。

因此 Signature 的核心作用是：

使接收方能够检测 Token 内容是否被未经授权地修改。

3. 为什么需要密钥

签名安全性的核心在于：

只有拥有正确密钥的一方才能产生能够通过验证的合法签名。

因此 JWT 的信任关系实际上建立在：
Signing Key
↓
Signature
↓
Verification Key
↓
Signature Validation

之上。

如果签名密钥泄露，攻击者可能构造新的合法 JWT。

因此：

JWT 的安全边界最终落在签名算法与密钥管理之上。

3.7.3 JWT 的认证流程

1. 用户认证

用户首先通过用户名、密码或其他认证机制完成初始身份认证。

↓

↓

2. JWT 签发

↓

↓

↓

3.7.5 JWT 安全分析

这一节是当前路线的重点。

JWT 的安全问题本质上可以归结为：
算法信任
+
密钥信任
+
签名验证
+
Claims 信任
+
Token 生命周期

1. alg:none

攻击者修改 Header：
{“alg”:”none”}

并移除 Signature。

如果服务端：

  • 信任 Token 中的 alg；

  • 没有固定允许的算法；

  • 错误接受无签名 JWT；

则可能导致伪造 Token 被接受。

核心成因：

服务端将不可信的 Token Header 错误地当成了安全策略。

2. 算法混淆

典型场景：
RS256
↓
HS256

RS256 使用：
Private Key → Sign
Public Key → Verify

HS256 使用：
Shared Secret → Sign / Verify

如果服务端错误地：

  1. 信任 JWT 的 alg；

  2. 没有固定算法；

  3. 混淆对称算法与非对称算法的密钥上下文；

则可能出现算法混淆问题。

其核心不是简单的：

“RS256 不安全。”

而是：

算法选择与密钥解释脱离了服务端既定的信任策略。

3. HMAC 弱密钥

HS256 使用共享 Secret。

如果 Secret 强度不足：
Weak Secret
↓
Offline Guessing
↓
Secret Recovery
↓
JWT Forgery

因此 HS256 的核心安全问题之一是：

Secret 的熵、保存方式和泄露风险。

3.7.6 JWT 与 Token 生命周期

当前阶段只建立三个核心概念。

1. Expiration

JWT 可以通过 exp 表示有效期。
Current Time ≥ exp
↓
Token Expired

2. Token Theft

如果有效 JWT 被窃取：
Attacker
↓
Valid JWT
↓
Server
↓
Authentication

攻击者可能在 Token 有效期内冒充原持有者。

3. Replay

Replay（重放）指攻击者不需要破解或修改 Token，而是重新使用已经获得的有效凭证。

因此：

JWT 的签名能够防止未经授权的修改，但不能天然防止合法 Token 被盗后重复使用。

这一点直接连接后续的 Token 安全与 Web 安全分析。

3.7.7 JWT 与 Cookie、Session、Access Token

当前只建立概念边界。

概念 所属层次 核心作用
JWT Token Format 表示结构化 Token
Cookie HTTP 状态机制 浏览器保存/携带数据
Session Server-side State 保存服务器端会话状态
Access Token Token Role 访问受保护资源
Refresh Token Token Role 获取新的 Access Token

核心关系：
Cookie 可以携带 JWT
JWT 可以作为 Access Token
JWT 可以携带在 Bearer 中

但：
JWT ≠ Cookie
JWT ≠ Session
JWT ≠ Access Token
JWT ≠ Bearer

3.8 Access Token 与 Refresh Token

在基于 Token 的身份认证体系中，Access Token（访问令牌）与 Refresh Token（刷新令牌）用于解决不同阶段的身份凭证需求。二者并非 JWT 的两种类型，而是按照使用目的与生命周期职责划分的两类 Token。

其核心设计思想是：

Access Token 用于访问受保护资源，Refresh Token 用于获取新的 Access Token。

该机制通过将“资源访问凭证”和“长期身份持续凭证”进行职责分离，在安全性、可用性与生命周期管理之间建立平衡。

3.8.1 Access Token 的概念

1. Access Token 的定义

    Access Token（访问令牌）是一种由授权方签发、用于证明客户端具有访问特定受保护资源权限的凭证。

其本质不是某一种固定的数据格式，而是一种Token 的用途定义。

因此：

JWT 可以作为 Access Token，但 Access Token 不一定是 JWT。

例如，一个 Access Token 可以采用：
eyJhbGciOiJIUzI1NiJ9…

形式的 JWT，也可以采用完全不可读的随机字符串：
8f72c9a1d6e4…

因此需要严格区分：

概念 定义
Token 身份、权限或授权状态的凭证统称
JWT 一种结构化 Token 格式
Access Token 用于访问受保护资源的 Token
Refresh Token 用于获取新的 Access Token 的 Token

2. Access Token 的核心作用

Access Token 的核心作用是：

在资源访问阶段向 Resource Server（资源服务器）证明当前请求具有相应的访问资格。

典型请求形式：
GET /api/user/profile HTTP/1.1
Host: example.com
Authorization: Bearer

服务端接收到请求后，需要验证：
Token 是否存在
↓
Token 是否有效
↓
Token 是否过期
↓
Token 是否由可信主体签发
↓
Token 的 audience 是否正确
↓
Token 是否具有所需 Scope
↓
允许 / 拒绝访问

因此：

Access Token 是资源访问阶段的授权凭证，而不是“登录状态”本身。

3.8.3 为什么 Access Token 通常设置较短生命周期

Access Token 本质上是一种资源访问凭证。

一旦泄露：
攻击者获得 Access Token
↓
在有效期内
↓
冒充合法客户端
↓
访问受保护资源

因此 Access Token 生命周期越长，Token 泄露后的潜在攻击窗口通常越大。

例如：
Access Token A
有效期：30 天

与：
Access Token B
有效期：10 分钟

在其他条件相同的情况下，B 的泄露窗口明显更短。

但是：

短生命周期并不能阻止 Token Theft（Token 窃取），只能缩短被窃 Token 的有效攻击窗口。

1. Refresh Token 的定义

**Refresh Token（刷新令牌）**是一种用于向授权服务器请求新的 Access Token 的长期凭证。

其核心目的不是访问业务资源，而是：

3.8.6 Refresh Token 为什么需要受到更严格保护

1. 长生命周期导致风险累积

假设：
Access Token：10 分钟
Refresh Token：30 天

攻击者获得 Access Token：
最多影响约 10 分钟

攻击者获得 Refresh Token：
可能持续获得新的 Access Token

因此 Refresh Token 的安全价值通常高于单个 Access Token。

2. Refresh Token 不应被当作普通 API 凭证

正常设计中：
Refresh Token
↓

Refresh Token
↓

这种职责分离能够降低 Token 被错误使用时产生的影响范围。

3.8.11 当前阶段必须掌握的安全结论

1. Access Token ≠ JWT

判定：真。

Access Token 是用途概念，JWT 是格式概念。

2. Refresh Token 可以直接访问业务 API

判定：通常错误。

Refresh Token 的设计用途是向授权服务器换取新的 Access Token，而不是作为普通资源访问凭证。

3. Access Token 越长越方便，因此越安全

判定：假。

生命周期越长，泄露后的有效攻击窗口通常越大。

4. Refresh Token 泄露比 Access Token 泄露更危险

判定：通常成立。

原因在于 Refresh Token 通常生命周期更长，并且可能持续换取新的 Access Token。

5. Refresh Token Rotation 可以彻底防止 Token Theft

判定：假。

Rotation 不能阻止 Token 被窃取，但可以降低长期重复使用风险，并能够在特定设计下帮助检测 Refresh Token 重用。

3.9 HTTP 缓存机制（HTTP Caching）

3.9.1 概述与规范基础

    HTTP 缓存机制的现行权威规范为 RFC 9111《HTTP Caching》（2022 年发布，取代原 RFC 7234），其定义了缓存存储（cache store）在响应可缓存性判定、缓存新鲜度（freshness）计算、缓存验证（validation）与失效（invalidation）方面的标准行为。缓存的本质是在客户端（浏览器缓存）、中间代理（forward/reverse proxy）与内容分发网络（CDN、edge cache）三个层级上，以牺牲一致性为代价换取时延与源站负载的优化，这一权衡在安全语境下会直接转化为攻击面。

从架构角度，缓存分为两类：

  • 私有缓存（private cache）：仅服务单一用户，通常位于浏览器本地，可存储包含用户身份信息的响应。
  • 共享缓存（shared cache）：服务多个用户，位于反向代理、CDN 边缘节点或企业出口代理，任何被共享缓存存储的响应都存在跨用户暴露的潜在风险，这是本节安全分析的核心关切点。

3.9.2 强缓存机制：Cache-Control 与 Expires

    强缓存（fresh cache，或称本地缓存）指客户端在不与源站通信的前提下，直接使用本地存储副本响应请求，其判定依据是响应的新鲜度生命周期（freshness lifetime）。

Cache-Control 是 RFC 9111 定义的主要控制首部，核心指令包括：

指令 语义
max-age=<seconds> 响应在生成后的新鲜时长
s-maxage=<seconds> 仅约束共享缓存的新鲜时长，优先级高于 max-age
no-cache 允许存储，但强制每次使用前必须完成验证（不等同于禁止缓存）
no-store 禁止任何形式的存储，是唯一真正阻止缓存的指令
private 仅允许私有缓存存储，禁止共享缓存存储
public 显式允许共享缓存存储，即便响应通常需要授权
must-revalidate 缓存过期后必须重新验证，禁止在验证失败时提供陈旧内容
immutable 声明资源在其新鲜周期内不会变更，抑制重新验证请求

Expires 首部是 HTTP/1.0 遗留机制，以绝对时间戳指定过期时间；当响应同时存在 Cache-Control: max-age 时，按照 RFC 9111 §5.2.2.1 与 §4.2.1 的优先级规则，max-age 具有更高优先级，Expires 被降级为兼容性回退。

安全要点：对于任何携带会话凭据、CSRF 令牌或个人身份信息（PII）的响应，必须显式声明 Cache-Control: no-store, private。仅依赖默认行为是不充分的——多数 HTTP 库与反向代理对未显式声明缓存策略的响应存在启发式缓存（heuristic caching，RFC 9111 §4.2.2）行为，可能导致认证页面被中间层意外缓存。

3.9.3 协商缓存机制：验证器与条件请求

协商缓存（validation-based caching）在本地副本过期后，通过条件请求（conditional request，RFC 9110 §13）向源站确认副本是否仍然有效，避免重复传输完整响应体。

  • Last-Modified / If-Modified-Since：基于资源最后修改时间的弱验证器，精度为秒级，无法感知同一秒内的多次修改，存在验证粒度缺陷。
  • ETag / If-None-Match：基于资源内容摘要的验证器，分为强验证器（strong validator）与弱验证器（weak validator，前缀 W/）。强验证器要求字节级完全一致，弱验证器仅要求语义等价，二者在范围请求（Range Request）与缓存投毒防护场景下的可靠性存在本质差异——涉及安全校验时应优先采用强 ETag。

服务端返回 304 Not Modified 表示验证通过，客户端复用本地副本；该状态码不应携带响应体，且必须保持与原始 200 响应一致的安全相关首部（如 Cache-Control），否则会造成策略不一致的隐蔽风险。

3.9.4 Vary 首部与缓存键的完整性

Vary 首部声明响应内容随哪些请求首部变化（如 Vary: Accept-Encoding, Cookie），共享缓存必须将这些首部纳入**缓存键（cache key）**的构成要素，否则会出现”缓存键未覆盖实际差异维度”的问题——这正是下文所述缓存投毒与缓存欺骗类漏洞的根本成因。若响应内容因 Authorization 或自定义身份首部而变化，却未在 Vary 中声明，共享缓存可能将 A 用户的个性化响应提供给 B 用户，构成会话内容跨用户泄露。

3.9.5 安全视角：缓存相关攻击面

（1）Web 缓存投毒（Web Cache Poisoning）

攻击者向源站发送包含未被纳入缓存键的输入（unkeyed input）——例如 X-Forwarded-Host、X-Forwarded-Scheme 等非标准首部——诱导源站生成包含恶意内容（如反射型 payload、重定向链接）的响应，该响应随后被共享缓存以合法请求的缓存键存储，从而对后续所有请求该资源的用户实施攻击。其攻击链的关键在于”输入影响响应内容，但未影响缓存键”这一不对称性。James Kettle（PortSwigger）在其”Practical Web Cache Poisoning”研究中系统化了该类漏洞的探测与利用方法论，是该领域的代表性工作。

（2）Web 缓存欺骗（Web Cache Deception）

与缓存投毒相反，该攻击利用路径解析歧义：攻击者构造形如 /account/profile/nonexistent.css 的请求，若源站的路由框架忽略路径后缀而返回动态私有内容，同时反向代理/CDN 仅依据扩展名（如 .css）判定为静态资源并将其缓存，则该包含用户隐私数据的响应会被写入共享缓存，攻击者可诱导受害者访问该构造 URL 后，自行请求同一 URL 获取被缓存的受害者数据。该漏洞最早由 Omer Gil 于 2017 年系统披露。

（3）敏感信息缓存泄露（Sensitive Data Exposure via Caching）

由开发者遗漏显式缓存策略声明导致，常见于：反向代理层默认缓存所有 200 响应而未区分内容类型；CDN 边缘节点对 API 响应启用了默认 TTL；负载均衡器健康检查逻辑绕过应用层缓存控制首部。此类问题不属于”利用型漏洞”，而是配置缺陷，但在渗透测试与红队评估中属于高频发现项。

3.9.6 防御性配置原则

  1. 对任何携带认证态或用户特定数据的响应，强制显式声明 Cache-Control: no-store，不依赖默认行为。
  2. 共享缓存层的缓存键必须完整覆盖响应内容的所有决定性输入维度，通过正确配置 Vary 或在代理层禁用对非标准首部的透传消除”unkeyed input”。
  3. 反向代理/CDN 层的静态资源缓存规则应基于内容协商结果与实际 Content-Type，而非仅依赖 URL 路径后缀模式匹配，以规避缓存欺骗类问题。
  4. 在安全审计与渗透测试流程中，应将”响应首部与缓存行为的一致性核验”纳入标准检查项，可结合 Burp Suite 的 Param Miner 插件对 unkeyed input 进行系统化探测。

3.10 TLS 握手流程（TLS Handshake）

3.10.1 协议定位与规范基础

TLS（Transport Layer Security）运行于传输层之上、应用层之下，为 HTTP 等应用层协议提供机密性（confidentiality）、完整性（integrity）与端点认证（authentication）保障。现行主要规范为：

  • RFC 8446，The Transport Layer Security (TLS) Protocol Version 1.3，IETF，2018。
  • RFC 5246，The Transport Layer Security (TLS) Protocol Version 1.2，IETF，2008（已被列为历史性文档，但仍广泛部署于兼容场景）。

TLS 1.3 相较 1.2 在握手阶段实现了结构性简化：往返次数（round-trip）由 2-RTT 缩减至 1-RTT，并引入 0-RTT（early data）模式，同时移除了静态 RSA 密钥交换、自定义 DH 参数、压缩、重协商（renegotiation）等已被证明存在安全隐患的机制。以下分别阐述 TLS 1.2 与 TLS 1.3 的握手流程，二者在安全模型上的差异是理解现代 TLS 部署实践的关键。

3.10.2 TLS 1.2 握手流程（Full Handshake，2-RTT）

  1. ClientHello：客户端发送支持的 TLS 版本、密码套件列表（cipher suite list）、客户端随机数（client random，32 字节）、压缩方法及扩展字段（如 SNI、ALPN、supported_groups）。
  2. ServerHello：服务端从密码套件列表中选定一项，返回服务端随机数（server random）与会话 ID。
  3. Certificate：服务端发送其 X.509 证书链，供客户端沿信任链（chain of trust）验证至受信任根证书颁发机构（Root CA）。
  4. ServerKeyExchange（视密钥交换算法而定）：在采用 (EC)DHE 密钥交换时，服务端发送临时公钥参数并以其长期私钥对其签名，为**前向保密（Forward Secrecy）**提供基础。
  5. ServerHelloDone：标志服务端首轮消息发送完毕。
  6. ClientKeyExchange：客户端发送其密钥交换所需参数（如 DHE 公钥，或在 RSA 密钥交换模式下的加密预主密钥 pre-master secret）。
  7. 双方分别依据 client random、server random 与 pre-master secret，通过 PRF（Pseudo-Random Function）派生出主密钥（master secret），进而派生出会话密钥、MAC 密钥与初始化向量。
  8. ChangeCipherSpec：通知对端后续记录将以协商密钥加密。
  9. Finished：双方各自发送经密钥加密的握手消息摘要，用于验证握手过程完整性、防止中间人篡改（Handshake 完整性校验）。

采用静态 RSA 密钥交换时，pre-master secret 由客户端生成并以服务端 RSA 公钥加密传输，若服务端私钥后续泄露，攻击者可回溯解密历史流量——这正是前向保密缺失的核心风险，也是 TLS 1.3 彻底移除该模式的直接动因。

3.10.3 TLS 1.3 握手流程（1-RTT）

TLS 1.3 强制要求密钥交换采用 (EC)DHE，废除静态 RSA 与自定义有限域 DH，握手流程如下：

  1. ClientHello：客户端在发送支持的密码套件、扩展字段的同时，基于对服务端支持的密钥交换组（key_share group）的预测，提前发送其密钥交换公钥参数（key_share extension），这是实现 1-RTT 的核心机制——客户端不再等待服务端指定参数后再响应。
  2. ServerHello：服务端返回其密钥交换公钥参数。至此，双方已具备计算共享密钥的全部信息，握手密钥（handshake secret）随即派生完成，自本消息起，服务端后续的所有握手消息均已加密（区别于 TLS 1.2 中证书等信息以明文传输）。
  3. EncryptedExtensions：传输不影响密钥协商但需要保密的扩展参数（如 ALPN 协商结果）。
  4. Certificate / CertificateVerify：服务端发送证书链，并以证书对应私钥对握手记录摘要签名，证明其持有证书私钥。
  5. Finished：服务端发送握手完整性校验值；随后客户端验证证书、计算相同密钥、发送自身的 Finished 消息完成握手。
  6. 双方由握手密钥进一步派生出应用数据密钥（application traffic secret），用于加密后续应用层数据。

0-RTT 模式：在与已建立过会话的服务端重连时，客户端可利用此前协商的 PSK（Pre-Shared Key）在 ClientHello 中直接携带加密的应用数据（early data），实现零往返时延，但该机制不提供前向保密与重放攻击（replay attack）防护，RFC 8446 §8 明确要求应用层对 0-RTT 数据的幂等性（idempotency）作出保证，否则应禁用该特性用于状态变更类请求（如支付、转账）。

3.10.4 密码套件与安全属性

TLS 1.3 将密码套件的构成大幅简化，仅描述 AEAD（Authenticated Encryption with Associated Data）算法与哈希函数（如 TLS_AES_128_GCM_SHA256），密钥交换与签名算法被移出密码套件命名，改由独立扩展字段协商，从而消除了 TLS 1.2 中因密码套件组合爆炸导致的弱组合误配置风险（如 TLS_RSA_WITH_RC4_128_SHA 类已知不安全组合）。

3.10.5 安全视角：握手阶段常见攻击面

  • 降级攻击（Downgrade Attack）：攻击者在中间人位置篡改 ClientHello 中的版本协商字段，诱导双方回退至存在已知漏洞的旧版本（如 POODLE 针对 SSLv3、DROWN 利用 SSLv2 交叉协议漏洞）。TLS 1.3 通过在 ServerHello random 末 8 字节嵌入降级检测标记（downgrade sentinel）予以缓解。
  • 证书验证绕过：客户端实现若未正确校验证书链、主机名匹配（Subject Alternative Name）或吊销状态（CRL/OCSP），将使中间人攻击（MITM）成为可行攻击路径，这是移动端与嵌入式设备 TLS 实现中的高频缺陷类型。
  • 弱随机数生成：client random / server random 或密钥交换私有参数若依赖低熵伪随机数生成器（PRNG），将直接威胁会话密钥的不可预测性，历史上的 Debian OpenSSL PRNG 漏洞（CVE-2008-0166）即为此类问题的典型案例。
  • SNI 明文暴露：ClientHello 中的 SNI（Server Name Indication）扩展在 TLS 1.3 基础握手中仍以明文传输，构成流量分析层面的隐私泄露面，ECH（Encrypted Client Hello，现行草案标准）旨在解决该问题。
  • 重放攻击（针对 0-RTT）：如 3.10.3 所述，0-RTT early data 缺乏握手层面的重放防护，需应用层或反向代理层（如通过一次性 ticket 或幂等性设计）加以缓解。

3.10.6 分析实践建议

在使用 Wireshark 进行 TLS 握手抓包分析时，建议：

  1. 结合 SSLKEYLOGFILE 环境变量导出主密钥，用于在 Wireshark 中解密应用层流量，便于验证握手正确性与后续数据加密行为。
  2. 重点核对 ClientHello/ServerHello 中的密码套件协商结果、证书链完整性，以及 TLS 1.3 场景下 key_share 扩展的密钥交换组是否符合预期（如 x25519、secp256r1）。
  3. 对比同一目标在不同客户端下的握手指纹（JA3/JA3S），可用于识别异常客户端行为或潜在的中间人代理注入。
