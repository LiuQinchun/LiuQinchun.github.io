1 Wireshark抓包分析

实验环境介绍：

    192.168.9.209是kali客户机，192.168.9.76是ubuntu服务器，服务端口8081搭载的DVWA靶场。

1.1 DNS

DNS总计查询了三次，也响应了三次：

  • No.880报文中客户机向默认网关发送了dns请求，事务ID 0x5dc1查询google.com的HTTPS记录。对应着No.884报文的默认网关响应报文，告知HTTPS等记录。

  • No.881报文中客户机向默认网关发送了dns请求，事务ID 0xfabd 查询google.com的IPv4地址。对应着No.883响应报文。

  • No.882报文中客户机向默认网关发送了dns请求，事务ID 033bf 查询google.com的IPv6地址。对应着No.885响应宝宝问，响应SOA表示未启动IPv6。

1.2 TCP连接全流程

1.2.1 TCP三次握手

由1.2中的图可知

  1. No.3 报文段中，客户端向服务器的 8081 端口发送 TCP SYN 报文段，请求建立 TCP 连接。由于 Wireshark 启用了相对序列号显示，此时 Seq=0。TCP Window接收窗口为 64240 字节，MSS 最大报文段为 1460 字节。

  2. 随后No.4报文段中服务端8081端口向客户端60798临时端口返回了SYN和ACK的Flags，Seq序列号为0，ACK确认号为No.3报文段中Seq值+1。表示我已收到客户端的同步请求，并且我同意你的连接。服务器通过 Ack=1 表示：客户端发送的 SYN（Seq=0）已经收到，我期望从客户端的 Seq=1 开始接收后续数据。

  3. 最终No.5报文段中，客户端向服务器8081端口发送ACK的Flags，Seq=1，Ack=1。客户端已经收到服务器的 SYN（服务器 Seq=0），因此期望服务器下一次发送的数据序列号为 1。Ack=1表示确认号值在No.4报文段中Seq=0+1得到。

就此TCP三次握手成功建立，可以开始传输数据。

TCB 传输控制块，打开后服务器/客户端进入监听（LISTEN）状态

SYN TCP报文标志位，该位为1时表示发起一个新连接
ACK TCP报文标志位，该位为1时，确认序号有效,确认接收到消息。TCP规定，在连接建立后所有报文的传输都必须把ACK置1
seq sequence number，报文初始序列号，代表发送的第一个字节的序号
ack acknowledgement number，报文确认序号，代表希望收到的下一个数据的第一个字节的序号

1.2.2 TCP四次挥手

由1.2中的图可知：

No.10 报文段中，客户端向服务器发送 FIN+ACK 报文段，Seq=407，Ack=1051，表示客户端已经没有更多数据需要发送，并请求关闭客户端到服务器方向的 TCP 数据流。

No.11 是服务器发送 FIN+ACK，既确认客户端的 FIN，又主动关闭服务器 → 客户端方向的数据发送。

No.12 客户端确认服务器发送的 FIN。服务器的 FIN 已经收到，我确认服务器不会再发送数据,客户端断连。

No.13 报文中，服务器向客户机发送了ACK的确认Flags，表示服务端无数据传递，服务器断连。

1.3.1 登录原理解析

    下图是登录DVWA靶场时抓取到的数据报文，前三次使用了不同的错误密码登录，最后一次是正确的登录（至于我为什么知道，当然是因为密码是我输入的啦，hhh~）

下面将会仔细的解释数据报文（三次错误密码登录，四个数据报文为一次登录周期，这里只仔细讲解第一次登录周期，为啥不讲完，当然是太麻烦了，哈哈，反正原理都一样的啦，喵~~~）：

概括：No.6、8、10、11是第一次错误登录周期，No.13、14、16、17是第二次错误登录周期，No.21、22、24、25是第三次错误登录周期。

No.36、38、40、44、53是成功登录周期，不同的是，No.38数据报文中身份认证通过，302临时重定向到index.php的网页。并向服务端提交GET请求报文，No.44就是服务端的响应报文。

（一）客户机发起POST登录请求

由下图可知，192.168.9.209客户机向192.168.9.76服务器发送POST请求，请求登录:192.168.9.76:8081/login.php页面，在这里，我刻意的使用了错误的登录密码向服务器发送了请求登录的数据报文。

（二）服务器发送302临时重定向

    服务端校验了用户名和密码发现对不上后就使用“302临时重定向“指向了\longin.php页面，指示客户端重新登录。

（三）客户机重新发送GET请求

    客户机响应服务端的302临时重定向，对服务端指定的URL页面发送GET请求。

（四）服务器响应客户机GET请求

    到了这一步，基本上密码登录失败的情况就结束了，服务端重新响应\login.php的登录页面，客户端重新输入用户名密码进行身份认证登录。

HTTP实验报告

实验时间： 2026年9月28日
客户端： 192.168.9.209
服务器： 192.168.9.76
服务器端口： 8081

正常登录：

  • 请求方法和路径： POST方法，对8081\login.php请求登录
  • 是否出现用户名和密码： 由于网站是HTTP协议，所以明文暴露用户名和密码
  • 是否携带 Cookie： 每次客户机向服务发送请求都会携带Cookie，并且Cookie值始终相同。
  • 服务器返回的关键内容： POST登录身份认证通过后，服务端返回302临时重定向，随后客户端下次向index页面发送了GET请求报文
  • 登录成功的证据： 客户端向index.php页面发送GET请求后，服务端返回的响应报文状态码200，页面成功加载

错误登录：

  • 请求和正常登录相比改变了什么： 302临时重定向指向login.php页面，准备重新登录

  • 是否使用了相同 Cookie： Cookie值始终相同

    “Cookie 值始终相同”不等于“Cookie 就是登录状态”。它可能只是 PHP 的会话标识。你还需要做三次对比：

    1. 登录前访问页面
    2. 登录成功后访问受保护页面
    3. 删除 Cookie 后再次访问受保护页面

    只有这样才能确认该 Cookie 是否真正决定登录状态。

  • 服务器返回的关键内容： 返回302临时重定向

  • 能否从抓包判断登录失败： 可以，抓包后观察是否有服务端的响应报文，状态码是否是HTTP 200 OK。或者观察302临时重定向指向哪里。

登录后访问：

  • 请求是否携带登录状态： 是，携带

  • 登录状态具体保存在哪里： 保存在Cookie

  • 不带该状态时会发生什么： 返回401未授权，302临时重定向指向login.php（根据理论，我猜的）

    错误登录不能只靠 302 判断。302 只是重定向，具体是成功还是失败，要看：

    • Location 指向 index.php 还是 login.php
    • 后续客户端请求了哪个页面
    • 后续请求是否成功访问受保护资源
    • 响应内容是否包含登录成功或失败信息

    失败登录后登录页也可能返回 200，所以“是否 200”不能单独作为登录成功标准。

安全结论：

  • HTTP 明文暴露了什么： 暴露了整个请求体和响应体，以及Cookie值，相当于裸奔。
  • 如果攻击者只能监听流量，能否复用登录状态： 直接套用Cookie，冒用身份，甚至还可以数据重发
  • 服务器应该如何降低风险： HTTPS 可以保护客户端到服务器之间的传输内容，降低网络监听导致的账号和 Cookie 泄露风险，但不能单独解决身份认证、权限控制和终端被入侵等问题。
